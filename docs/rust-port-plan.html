The whole plan rests on one property of this codebase, which I checked before writing anything else: every test in ObjectUtilsTests constructs its object through a factory function and asserts only through an abstract interface. ElfFileImpl lives in an anonymous namespace; no test can see it. That means the existing 659-line ElfFileTest.cpp is already an implementation-independent conformance suite, and a Rust implementation can be dropped behind CreateElfFile() and judged by it without editing a single test.

The mechanism: one factory, three backends

The obvious way to do this is to build a second copy of each test target linked against the Rust library. It works, but it only proves that both implementations pass the same assertions — not that they produce the same answers. Two implementations can both satisfy EXPECT_EQ(symbols.size(), 4) and still disagree about every address.

So instead: keep one factory, and give it a third mode that runs both and compares.

Three small things make this work, and none of them touches a test:

  1. Split the headers into their own target. ObjectUtilsInterface carries include/ObjectUtils/*.h and nothing else, so the Rust shim can implement ElfFile without depending on the LLVM implementation. Pure BUILD refactor, no source change.
  2. Rename the existing factory to CreateElfFileCpp() in an internal header, and add a ~60-line Backend.cpp whose CreateElfFile() dispatches. The public signature in include/ObjectUtils/ElfFile.h does not change, so all 16 dependents keep compiling untouched.
  3. Default to cpp. An unset variable means today's behaviour, exactly. Nothing in production changes until a phase is finished and the default is flipped deliberately.
Why the strangler, not a big-bang subclass

RustElfFile holds a std::unique_ptr<ElfFile> built by CreateElfFileCpp() and overrides methods one at a time. On the first commit it might override three of eleven and delegate the rest. That keeps :ObjectUtilsTestsRust passing from day one, makes every commit independently mergeable, and turns "is the port finished" into a countable question: how many methods still delegate. When the count reaches zero the delegate is removed and ElfFile.cpp can be deleted.

Four verification gates

Each is cheap to run, runs in CI, and catches a different class of mistake. A phase is not done until all four are green.

1

Conformance — the existing suite, three ways

bazel test //src/ObjectUtils:all runs the same 66 test cases three times. This catches anything the original authors thought worth asserting, which for ElfFileTest is a lot: load bias with and without program headers, .eh_frame versus .debug_frame, compressed debug sections, inlined line info, and the exact error strings.

Discipline this imposes: the Rust backend must reproduce Orbit's own error text verbatim, because eight assertions match on it — for example "Unable to get load bias of ELF file: \"%s\". No executable PT_LOAD segment found.". All eight are Orbit's strings, not LLVM's, so this is bounded work rather than an impossible constraint. Never surface an object or gimli error where a test expects an Orbit one.

2

Differential — a real corpus, not a curated one

A symbol_dump tool that takes a path and writes ModuleSymbols as text proto, plus a sh_test that runs it under cpp and rust over every ELF it can find and diffs the pair. Corpus: the 34 files in src/ObjectUtils/testdata, plus everything Bazel just built in bazel-bin, plus /usr/lib/x86_64-linux-gnu/*.so* when present.

Why this and not just gate 1: the curated testdata is a dozen small binaries chosen to exercise specific code paths. A real libQt5Core.so or a stripped-and-debuglinked libc exercises combinations nobody wrote a test for. This is where object-versus-LLVM disagreements about odd section layouts will actually show up.

3

Fuzz parity — the property the fuzzer was already for

ElfFileLoadSymbolsFuzzer.cpp already exists and calls CreateElfFileFromBuffer on arbitrary bytes. Point it at both mode: now it is not just "does this crash" but "do the two implementations agree, or fail in the same way, on malformed input". Both implementations must reject the same buffers.

Note: the fuzzer is a CMake-era file with no Bazel target. Part of this phase is giving it one — worth doing regardless of the port.

4

Performance — measured, not assumed

Criterion benches inside the Rust crate for micro-level work, plus an A/B harness that loads symbols from the same corpus N times under each backend and reports wall time and peak RSS. Because the backend is an environment variable, that is one binary run twice — no separate build.

Pass criterion: Rust is not slower on LoadDebugSymbols for a large module, and does not use more peak RSS. If it is slower, the phase does not merge until it isn't — "correctness first, performance later" is how a port quietly becomes a regression.

Where the Rust lives

A new top-level rust/ workspace, deliberately separate from src/OrbitLiveViewer. Two reasons: the symbol parsers should not share a lockfile with a tokio-and-wgpu dependency tree, and keeping the new work in one directory is what makes the side-by-side comparison legible.

The C++ shims live under rust/ rather than beside the module they serve. That is slightly unusual, and it is the right trade here: it keeps src/ObjectUtils at one new file (Backend.cpp) and one changed BUILD.bazel, so git diff on the C++ tree stays readable for the whole port.

One thing to decide before Phase 0

A third crate_universe repository (@crates for py-spy, @live_crates for the viewer, @orbit_crates for this) is one more lockfile to keep current. The alternative — folding these crates into the existing viewer workspace — couples the symbol parser's dependency resolution to eframe's. I would take the third repository, but it is worth being deliberate about, because merging them later is harder than splitting them now.

Phase 0 — scaffolding

No behaviour change, no Rust logic. This phase exists so that Phase 1 is a single small commit rather than a single large one.

  • rust/ workspace, rust-toolchain.toml, @orbit_crates wired into MODULE.bazel next to the two that already exist.
  • A orbit_dual_backend_test() Starlark macro in bazel/: given a cc_test's attributes and a backend variable name, it emits the three targets so no BUILD file repeats itself three times.
  • A no-op Rust crate with one FFI function and one rust_test, linked into a throwaway cc_test, to prove the toolchain end to end before any real code depends on it.
  • CI: add the new targets to .github/workflows/build-and-test.yml. They should be gating from the first commit — a non-gating conformance suite is not a gate.

Phase 1 — the 73-line pilot

orbit_module_utils::ParseMaps is the smallest real thing in the tree that is worth porting, and it is close to a perfect first target:

// src/ModuleUtils/include/ModuleUtils/ReadLinuxMaps.h
[[nodiscard]] std::vector<LinuxMemoryMapping> ParseMaps(std::string_view proc_pid_maps_content);

A pure function. Text in, five integers and a string out, per row. No I/O, no allocation policy to match, no error type to reproduce — it cannot fail, it just returns fewer rows. 73 lines of implementation, 89 lines of test, four test cases. If the machinery from Phase 0 works, this lands in a day; if it doesn't, it fails cheaply and visibly.

It is also genuinely on the hot path — ReadModules parses the whole maps file for every process listed, and the process list is polled — so it gives gate 4 something real to measure on the first try.

FFI shape: one call in, one flat buffer out. Rust returns a count plus a pointer to an array of { start, end, perms, offset, inode, path_offset, path_len } and a separate string blob; the shim walks it once building std::vector<LinuxMemoryMapping>, then frees. No per-row allocation across the boundary, no ownership subtleties, and it is the same pattern every later crate will use.

Phase 2 — ObjectUtils, and deleting LLVM

This is the phase with the payoff. I checked the dependency graph specifically: //bazel/deps:llvm has exactly one dependent in the entire tree, and it is //src/ObjectUtils. There is one other LLVM include anywhere — llvm/Demangle/Demangle.h in CaptureClient/CaptureEventProcessor.cpp, which does not even declare the dependency and picks it up transitively.

2g is the long pole, and it is not optional

It would be convenient if PDB reading were Windows-only, but it isn't. CreateSymbolsFile tries CreatePdbFile unconditionally on Linux, and SymbolsFileTest asserts on the failure message — because Orbit does Wine/Proton mixed-callstack profiling and has to read PE and PDB for Windows modules running under Proton on a Linux host. So LLVM cannot be deleted until the pdb crate covers what PdbFileLlvm does. That crate is mature for symbol and address lookup, which is all Orbit asks of it, but this is the stage most likely to need a fallback — and the fallback is ugly: keeping LLVM for one library.

Phase 3 — the pure-logic half of LinuxTracing

Seven classes in src/LinuxTracing do no I/O, open no file descriptors, and touch no kernel interface. They are algorithms with unusually good test coverage — 1,355 lines of implementation against 3,053 lines of test, a ratio of better than two to one.

ClassImplTestWhat it does
PerfEventQueue220422Heap-of-queues merge of per-CPU streams into one timestamp order
ThreadStateManager334593Per-thread state machine over sched tracepoints
LeafFunctionCallManager238596Frame-pointer fixup for leaf frames
UprobesReturnAddressManager227799Stitches return addresses displaced by uprobes
ContextSwitchManager122256Pairs switch-in and switch-out into slices
UprobeAddressMap122182Address range bookkeeping
UprobesFunctionCallManager92205Entry/exit pairing into function calls

The FFI here is different in kind from Phase 2, and worth thinking about before starting rather than during. These classes sit on the hot path and traffic in PerfEvent, a large C++ variant. Copying it across a boundary per event would swamp any gain.

The shape that works: the Rust side never sees a PerfEvent. It owns only the ordering keys — (timestamp, stream_id, u64 handle) — and the C++ side keeps the events in a slab, passing indices. PerfEventQueue becomes a Rust data structure over three integers per element, which is what it actually is; the payload never moves. Same for the state managers, which key on (tid, timestamp, state).

This phase is also where gate 4 earns its keep, because it is the one place where a Rust port could plausibly be slower — an FFI call per event is not free, and the batching has to be designed rather than discovered.

The log, and what counts as proof

Every phase is written up in docs/blog/ as it happens. The posts are not a summary written afterwards — they are the record, and the discipline they impose on the work is the point: a phase is not finished until its numbers are reproducible by someone else.

Four rules, chosen because each one is a way the write-up could otherwise become worthless:

  1. No claim without a committed number. Every figure a post cites comes from a script in scripts/ whose output is checked in under docs/blog/metrics/. A reader can re-run it and disagree.
  2. The C++ test files are never edited. They are the specification. A port that adjusts its own exam has not passed anything — and this is the single easiest corner to cut, because a failing assertion always looks like it might be the test's fault.
  3. Numbers that get worse get reported. A strangler port makes the tree bigger before it makes it smaller. Hiding that would make the good numbers worth less, and the first post already reports a dependency count going up by 56 and a module gaining 137 lines.
  4. Every hurdle is written down, including the ones that are self-inflicted. Post 01 records eight, of which two were bugs in the new code and one was a bug in a new test.

The baseline snapshot was taken before any Rust existed, on the commit the branch was cut from. That is what makes every later delta meaningful, and it is the one measurement that cannot be retaken.

The claims this is designed to be able to prove

Fewer dependencies: deps(//src/ObjectUtils) was 5,843 targets across 17 external repositories at baseline; deps(//src/Service:OrbitService) was 22,220 across 334. Phase 2h should move all four numbers down, and //bazel/deps:llvm's dependent count from 1 to 0.

Fewer lines: tracked per module, and expected to rise during a phase and fall at its end when the C++ is deleted. Reporting the rise is what makes the fall believable.

No re-implemented error types: ErrorMessageOr appears 1,352 times and exists because C++ had no Result; the OrbitBase headers that std, tokio or rayon would provide come to 2,963 lines. Both counts are in every snapshot, so the reduction is a measurement rather than an assertion.

Faster, or at least not slower: one A/B benchmark per ported module, with the mechanism explained in the post. A number without a mechanism is a coincidence.

What can go wrong

object and gimli are not LLVM. They are excellent and they are what the Firefox profiler and Sentry run on, but they are not bug-for-bug identical. The likely friction points are already named by the test suite: CompressedDebugInfo (the Bazel port had to patch LLVM just to turn zlib on for SHF_COMPRESSED), LineInfoInlining (inlined frames in DWARF line tables), and DWARF 5 forms. Gate 2 over a real corpus is how these surface early rather than in a user's capture.

Error strings are load-bearing. Eight assertions match on exact Orbit error text. That is a small, bounded requirement, but it is easy to forget until CI fails — and easier still to "fix" by editing the test, which would quietly destroy the value of gate 1. The rule: the test file is never edited during a port. If a test seems wrong, that is a separate commit, made against the C++ backend, before the port touches it.

both mode has a cost. Running two implementations on every call roughly doubles the work in that suite. That is fine for a test target and would not be fine anywhere near production, so the mode must be reachable only via the environment variable and never become a default.

The PDB stage may not land. Covered above. If pdb cannot reproduce PdbFileLlvm, LLVM survives for one library and the build-time win mostly evaporates while the correctness and dependency wins remain. Worth deciding in advance whether that outcome is acceptable, because it changes what "finished" means for Phase 2.

The C++ never gets deleted. The failure mode of a strangler is that both implementations live forever and every change has to be made twice. The countermeasure is the delegation counter: it is a number, it should only ever go down, and when it reaches zero the deletion commit is already written.

The first pull request

Scoped so it either works or fails visibly, in about a day, with no Rust logic in it at all beyond a parser that four existing tests already specify.

PR 1 — scaffolding plus the pilot

  1. Create rust/ — workspace, rust-toolchain.toml, @orbit_crates in MODULE.bazel, a README explaining the backend switch.
  2. Add bazel/dual_backend.bzl — the orbit_dual_backend_test() macro that emits the three cc_test targets from one set of attributes.
  3. Write rust/crates/orbit-maps — parse_maps(&str) -> Vec<Mapping>, plus Rust unit tests ported from ReadLinuxMapsTest.cpp so the crate stands alone.
  4. Write rust/ffi/orbit-maps-ffi — one extern "C" entry point, flat output buffer plus string blob, one free function, a hand-written header in the pyspy_ffi.h idiom.
  5. Write rust/shims/ModuleUtilsRust — ParseMapsRust() returning std::vector<LinuxMemoryMapping>.
  6. Add src/ModuleUtils/Backend.cpp — ParseMaps() dispatches on ORBIT_MAPS_BACKEND; both compares element-wise and ORBIT_CHECKs. Default cpp.
  7. Emit the three test targets for ReadLinuxMapsTest.cpp and add all three to CI as gating.
  8. Add rust/tools/ab_bench with one case: parse a large real /proc/self/maps N times under each backend, print wall time and peak RSS. Paste the numbers in the PR description.

If that PR is green in all three modes and the benchmark does not regress, everything after it is the same moves at larger scale. If it isn't, the problem is in the machinery rather than in 73 lines of maps parsing, and it is worth finding out there.

Say the word and I'll start on it. My suggestion is to do PR 1 exactly as scoped — resist adding ObjectUtils to it, because the point of PR 1 is to be small enough that when something breaks it is obvious which of the eight items broke it.
