Two Phantoms and a Real Five Percent

An agent drove Orbit's profile→hook→change→measure loop against Stockfish a second time, this time with a written trace of every step, before/after captures, and clean end-to-end runs with no profiler attached. It retracted a win it had claimed the day before, lost three well-motivated prefetch experiments to the gate, found two bugs in the loop's own tooling, and ended with one gain nobody can argue with: +4.3% accepted by the gate, +6.0% in 16 of 16 interleaved runs, fingerprint identical. That gain is Stockfish's own profile-guided build. What the loop actually produced is the method that tells the real gain from the two phantoms.

Every number below is copied from tool output recorded in docs/optimize-loop/experiments/stockfish-run2/trace.md, appended as it happened. Box: i9-13900KF (8 P + 16 E cores), shared with the owner's other work while this ran. Tree read at 3323c24f3, branch loop. Target: official-stockfish/Stockfish at 17a6c8f, built out of tree, left clean.

The brief was blunt: run again, make a trace of what you did, before/after Orbit captures, a blog post. Try to find an undeniable performance gain in Stockfish. Also measure end-to-end runs without instrumentation before/after to make sure it worked. The previous run had ended with a claimed +2.56%, 14/14 paired wins from adding __restrict to one NNUE function. This post starts by taking that claim apart, because "undeniable" is a standard the first run did not meet, and the only way to earn it was to find out why.

The loop, and who does what

The tooling in tools/optimize-loop is an MCP server with seven tools. Orbit gathers the data; a small gate decides; the agent supplies the hypotheses. This run used all seven, plus two things Orbit cannot do yet, which are called out where they appear.

That is the skill's first rule with real numbers: a function called a million times a second cannot be timed by hooking it; the hook overhead becomes the measurement. Hook the caller, and let sampling say the leaf is hot.

The first phantom: __restrict

Run one had ended on a code change with a plausible story. apply_combined reads one accumulator and writes another that provably do not alias, so telling the compiler (__restrict) should let it keep tiles in registers across the store passes. Measured single-shot: +1.53%, gate ACCEPT. Confirmed interleaved: +2.56%, 14 of 14. This run put the same patch, a sibling patch for update_accumulator_refresh_cache (where the store sits mid-loop, so the story was stronger), and both together through the MCP tools again.

Then how did run one get 14 of 14? The most likely answer is in the next section: the interleaving was unpinned on a hybrid CPU, and whichever binary launched second in each pair tended to land somewhere slightly different. Fourteen coin flips coming up the same way is a strong signal of something, but not necessarily of the thing you changed. The retraction stands on the code diff, not on the re-measurement: a change that does not change the instructions cannot own a speedup.

Retracted

The experiment write-up from run one said the __restrict change was "real and reproducible" and "upstreamable on its own". It is neither. The document is corrected in the same commit as this post.

A noisy box, and what is deterministic on it

The box that ran this is a 13900KF: eight performance cores with hyperthreads, sixteen efficiency cores, a powersave governor, and two of the owner's processes taking a core and a half between them for the whole session. An unpinned single-thread bench lands wherever the scheduler puts it, and the same binary read anywhere from 1.385 to 1.495 M nodes/s inside one batch of ten. That is an 8% spread on a benchmark whose interesting effects are 1–2%.

Three controls came out of this and went into the skill. Pin the bench to one P-core whose hyperthread sibling is idle (taskset; a four-second /proc/stat survey picks the core). Read instructions:u next to nodes/s, so a "win" that retires the same instructions is suspect before it is celebrated. And let the CPU cool for twenty seconds after a sixteen-core build, because the first benchmark after a build is measurably slower and the loop was benchmarking immediately.

Where the misses are

With the phantom gone, the honest position was: a 37% function, tightly coded, in a program tuned by a thousand people. To get a hypothesis with a mechanism, I needed something Orbit does not yet do: attribute cache misses to instructions. perf record with the precise event mem_load_retired.l3_miss:upp does that. The owner's rule is that Orbit is the profiler unless it cannot do the job; this is one of those, and it is now on the list.

Three prefetches, three rejects

If the psq columns miss because nobody asked for them early, ask for them early. Three ways, each behavior-preserving (integer adds in the same order; fingerprint identical throughout), each measured pinned with instructions:u, cycles:u and nodes/s over six alternating pairs:

variantwhere the prefetch is issuedinstructionscyclesnpswhy it lost
P1all 32 lines of each psq column, just before apply_combined+2.1%+1.7%−1.3%up to 128 prefetches in a burst into ~16 fill buffers, microseconds before the loads: queueing, not lead time
P2next tile's 8-line chunk, inside the tile loop+7.9%+2.0%−2.1%the eight loads of a chunk already issue back to back; the core had the memory-level parallelism, the prefetch only added work
P3at Worker::do_move, next to the TT prefetch, for from/to/captured × both perspectives+3.4%+2.6%−3.9%real lead time, but 12 KiB per node for updates that often never happen (pruned nodes, TT hits): pollution

The instruction column is the useful one. Each variant did exactly the extra work its prefetch count predicts, and none of it bought anything: the stall that PEBS attributes to those loads is not a serial latency the core is waiting on, it is eight misses in flight that the out-of-order window already overlaps with the threat-column work. A precise profile tells you where the misses are; it does not tell you they are on the critical path. Stockfish's own developers presumably found this the same way, and left the psq columns alone. Three rejects, all reverted; the patches are kept in the experiment folder as the record of what was tried.

The real five percent

That left the behaviour-preserving levers that change the build rather than the source. -mtune=native did nothing (−0.27%, 6/16 interleaved). Stockfish's profile-build (PGO) is the other, and the gate's three attempts to accept it are the most instructive part of the run.

Run one is the gate doing its job on a bad box: something took the core for twenty seconds during the first noise batch (four runs at 0.90 M nodes/s), the measured floor came out at 16%, and a 9% gain was correctly refused as unprovable on that evidence. Run two is a bug in the loop, described below: the "baseline" it measured was the PGO binary. Run three, with clean builds and a cool-down, accepted.

And then the confirmation the brief asked for: sixteen rounds, three binaries, rotated order, pinned, and no profiler attached at any point.

Is that the "undeniable gain in Stockfish" the brief asked for? It is undeniable, it is in Stockfish, and it is behavior-preserving. It is also not a discovery: profile-build is the build Stockfish releases use, and the loop's baseline was the plain build. What the loop found is not that PGO is faster; it is a method that can tell a 4% real gain from a 2.5% imaginary one on a shared machine, and every one of the five code changes it tried was, correctly, sent back.

The after-profile is a different shape, not a smaller one. propagate is gone from the table because PGO inlined it into Network::evaluate; search and next_move grew because their hot paths were laid out and inlined more aggressively. The 37% leaf is untouched in both, which is consistent with everything above: that function is memory-bound and already tight, and the win came from everything around it.

What the loop got wrong about itself

An incremental rebuild compared PGO to PGO. optimize_rebuild ran make build over object files left by the previous profile-build; make saw them as up to date and linked them, so gate run two's "baseline" was the PGO binary and the PGO "gain" was +0.28%. Build commands for build-level variants now clean first, and the finding is in the skill: an incremental build does not see a flag change.

optimize_rerun_compare rebuilt implicitly with no way to say no. The noise-floor batches re-measure the same binary; they were going through a build each time. The tool now takes skip_build, and the driver passes it for every re-measure.

A fresh capture reported another process's losses. Every hooked run, on both days, showed the status line "DROPPING EVENTS: 1071584 scope records lost", including a coarse hook with 24 calls in a brand-new service. The number never changed. The owner has a five-hour-old samples process with its scope ring still in /dev/shm; the service discovers every segment and, on first drain of one that has been written far past its capacity since nobody was reading, counts the lap as records lost. Not this capture's loss, and the status line should not carry it. Filed as a follow-up: start a discovered segment's cursor at its current write position, and attribute losses per producer.

Two things Orbit could not do, that the run needed: instruction-level attribution within a function, and precise cache-miss sampling. Both came from perf. The address is in every sample Orbit records; a per-address view of a selected function is the next feature this loop wants.

Lessons, now in the skill

  1. Diff the code before you benchmark the change. If the instructions did not change, the speedup is not yours. Five bytes is not a mechanism.
  2. Read retired instructions next to throughput. They are deterministic on a deterministic bench, and they separate "does less work" from "got lucky" for free.
  3. Pin, cool down, interleave. One P-core with an idle sibling; twenty seconds after a parallel build; rotate binaries per round and count paired wins. Sixteen of sixteen is a result; fourteen of fourteen unpinned was not.
  4. A precise miss profile locates misses, not the critical path. Eight misses already in flight do not get faster by being asked for again.
  5. Clean builds for build-level variants, and a re-measure must never rebuild.
  6. Report rejects and retractions in full. This run's most useful output is a corrected document and five patches that did not work, kept so nobody tries them next.

The Stockfish tree is clean. The experiment folder holds the trace, the five patches, the driver, the interleaved benchmark script and its data, and both configs. The PGO binary is the one to run.
