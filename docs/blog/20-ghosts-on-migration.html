Ghosts on Migration

A hooked function that calls nothing kept showing up nested inside itself, dozens deep, but only on some threads. The stack pointer every uprobe hit carries said what happened: the kernel was dropping a hit, an entry or a return, and one dropped hit is a ghost that never leaves. Here is how the timeline made it obvious, what the kernel does with a uretprobe, and the pairing that heals it.

The filter and the frame pairing are in rust/crates/orbit-service/src/uprobes.rs, behind one switch (the Dedupe pill, or uprobe_duplicate_filter in the capture request). Two real captures are embedded below; drag to pan, wheel over the ruler to zoom, click a thread to open its rows.

Post 19 built a test that holds a capture to a known number of calls. This is the bug it was built for. Hook four Box3D functions with kernel uprobes, run the physics on more threads than cores, and the timeline fills with scopes that cannot be right: b3World_Step, the outermost call, appears nested inside another b3World_Step, and inside that one another, on some threads a dozen deep. The function calls no copy of itself. The nesting is a lie, and it is a lie the profiler tells confidently, with durations and a call tree, which is worse than telling nothing.

See it

Two captures of the same workload, four functions hooked, five seconds each. The only difference is one switch. Open a thread in each and read the depth of b3World_Step: in the first it is often one, two, three levels down, a scope inside a scope of the same name; in the second it is always at the top, where it belongs.

These are not renderings of stored images; they are the real capture frames a connecting viewer would have received, opened by the viewer with no service behind it. The report panel's Flat and tree tabs are computed in the browser from the sampled callstacks the capture also carries, which is why the sampling profile looks identical in both: sampling was never wrong. Only the instrumented scopes were.

Why it was easy to spot

A sampling profiler would have hidden this. A miscounted call is a rounding error against a million samples. But dynamic instrumentation draws every call as a scope on the thread that made it, at the depth it ran, so a single accounting mistake is not a number that drifts — it is a box drawn in the wrong place, and it stays there. When b3World_Step sits one level too deep, everything it appears to contain is one level too deep with it, and the eye catches the whole column at once.

Better still, Orbit draws the scheduler under the threads. Line the depth changes up with the scheduler slices and a pattern appears: in the capture that first showed this — a real Box3D run, not the synthetic one above — every one of the 47 depth changes landed 10 to 20 microseconds after the thread resumed on a different core. The bug had a signature, and the signature was thread migration. That is the kind of clue a flat profile cannot give you, because a flat profile has no threads, no time and no cores on it.

The obvious fix, which fixed nothing

C++ Orbit has a workaround for exactly this. Its UprobesUnwindingVisitor keeps, per thread, the stack pointer, instruction pointer and CPU of the last uprobe, and drops an incoming entry that repeats the last one's sp and ip from a different CPU:

// We are seeing that, on thread migration, uprobe events can sometimes be
// duplicated: the duplicate will have the same stack pointer and instruction
// pointer as the previous uprobe, but different cpu. Discard the second one.

The reading is that a thread migrating inside the probe's window makes one logical hit surface in two per-CPU ring buffers. Orbit opens its probes per CPU, so two buffers for one hit is plausible. The rule was ported to the Rust service verbatim, and on the ghost capture it dropped nothing. Not a few. Zero. Every run since, synthetic or real, reports the same: filter off, 0 migration duplicates went through. Whatever was wrong, it was not a duplicated stack pointer.

Reading the raw hits

The service can write every probe hit to a file before any pairing — timestamp, thread, CPU, function, entry or return, and the stack pointer and instruction pointer the sample carries (--uprobe-dump). With the file in hand the accounting is arithmetic. The stack grows downward, so a nested call's stack pointer is strictly below its caller's, and a return leaves exactly the frame its entry opened. Walk a thread's hits keeping a stack of open frames, and every place the nesting breaks is either an entry sitting at or above a frame that is still open — its return was never delivered — or a return for a frame nothing opened — its entry was never delivered.

On a filter-off capture of about 1.7 million hits, the walk found the breaks, and they were all of one kind: hits missing. Entries with no matching return, returns with no matching entry, and not once two entries sharing a stack pointer. The kernel was not doubling hits. It was losing them, entries and returns alike, and a lost hit is unrecoverable at the ring: the data never arrived. The duplicate filter was built for a bug this box does not have; the bug this box has is a hole.

A hole is worse than a double, because it is silent and it is permanent. Drop one return and the entry it belonged to never closes; the next call on that thread opens inside it, and the one after that inside it, and the depth is off by one for the rest of the capture — or by two, or by twelve, one per hole. That is the pile of ghost nesting in the first embed above, and it is why a single lost hit near the start of a busy thread taints everything that thread does afterward.

What the kernel does with a uretprobe

Chasing the hole into the kernel is where honesty has to take over from proof. The delivery path is per-CPU: a uprobe fires, the handler runs, and __uprobe_perf_func writes the sample into this_cpu_ptr(call->perf_events) — the ring of whatever CPU the thread is on at that instant. Nothing there drops a hit on its own. The interesting half is the return probe, because a uretprobe is not a breakpoint at the return address; it is a hijack. When the entry fires, prepare_uretprobe (in kernel/events/uprobes.c) rewrites the return address on the user stack to point at a trampoline, and pushes a return instance onto a per-task list. And it has three ways to give up, each a silent goto free:

if (!get_xol_area())                       goto free;   // no execute-out-of-line page
if (utask->depth >= MAX_URETPROBE_DEPTH)    goto free;   // nesting limit
orig_ret_vaddr = arch_uretprobe_hijack_return_addr(trampoline_vaddr, regs);
if (orig_ret_vaddr == -1)                  goto free;   // could not write the user stack

The third is the one that matches a migration. Hijacking the return address means writing to the user stack from kernel context, and if that page is not writable at that instant — a fault, a race — the hijack returns -1 and the return probe is quietly dropped: the entry was recorded, the return will never come. That is a lost return, the exact shape of the ghost. There is also the arming edge, which the synthetic captures here hit hardest: when probes are installed on a process already running, threads that are mid-call when the breakpoint lands hit a return the kernel has no entry for, or an entry whose return address was already on its way back. Both are holes, and both cluster right after arming, which is where this kernel puts most of them.

The migration signature from the original capture points past all three, at the class of bug the arm64 kprobes series "fix XOL preemption window" describes: probe state kept per-CPU, executed out of line while the thread can still be preempted, so a migration inside that window is handled on a CPU that never set the state up. Same shape, different architecture; the upstream fix disables preemption across the single-step so the pair cannot split across CPUs. I could not pin the exact x86-64 line that loses a steady-state hit on this kernel — the reproducible drops are the arming edge and the prepare_uretprobe paths above — and saying more than that would be dressing a guess as a finding. What is certain from the raw hits is the shape: the kernel loses whole hits, correlated with scheduling, and never doubles them.

Pairing by frame, not by count

If the kernel will lose hits, the service cannot pair entries to returns by counting them; it has to use something that survives a hole. The stack pointer is that thing. Every uprobe sample already carries it, so the pairing keeps, per thread, the stack of open frames by their stack pointer, and lets the geometry decide:

  • An entry at or above an open frame proves that frame's return was lost: a real nested call would sit strictly below it. The stale frame is closed and counted as an unclosed entry, and the new call opens at the right depth.
  • A return for a frame nothing is open at proves its entry was lost: closing the caller instead would be the ghost. The return is dropped and counted as an orphan.

Depth is correct from the next hit onward, so a hole costs one scope, not the rest of the capture. The C++ stack-pointer duplicate rule still runs in front of it — it costs nothing to keep and it is the right fix if a kernel ever does double — and both sit behind one switch, on by default, so the effect can be measured. The status line after a capture says what happened either way: with the filter on, N calls; a duplicate entries dropped, b entries with no return discarded, c returns with no entry dropped; with it off, how many hits went through that the filter would have caught. The two embeds above are those two status lines made visible.

What is proven, and what is not

Proven, from the raw hits and the two captures: the ghosts are lost uprobe hits, not duplicated ones; a lost hit shifts every later scope on its thread until it is healed; the frame pairing heals it, taking one capture from 41% of a function's scopes wrongly nested to none. Correlated, strongly, in the capture that started this: the losses follow thread migration. Not pinned: the exact kernel path that loses a hit at steady-state migration on this box — on this kernel the synthetic reproductions concentrate the losses at probe arming, and the clean steady-state migration signature came from a heavier machine's real capture. The fix does not depend on which it is. It assumes the kernel can lose any hit, and keeps the timeline honest when it does.
