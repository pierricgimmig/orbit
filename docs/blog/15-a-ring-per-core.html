A Ring Per Core

Manual instrumentation has to cost almost nothing or people turn it off. Here is the write path, measured honestly at sixteen nanoseconds a scope, the two places the obvious design is unsound, what rseq is and what it would actually be worth, and the bug that only appeared when someone asked the right question.

A profiler's manual instrumentation is the feature people use most and trust least. Every ORBIT_SCOPE in a hot loop is a bet that the measurement costs less than the thing being measured, and the moment that bet stops paying, the macros get commented out and the profiler stops being used. So the write path is the whole design. Everything else — ordering, merging, nesting — is the consumer's problem, and the consumer is allowed to be slow.

The shape of it

An instrumented process writes events into its own shared-memory segment. The service maps that segment, drains it, merges it into one globally ordered stream, and hands it to the timeline. The two sides never talk, never synchronise, and never block each other.

One ring per core, not per thread. A thread-per-ring design is simpler and genuinely single-producer, but it scales with something you do not control: a process with four thousand threads gets four thousand rings, and the merge becomes a four-thousand-way heap. Cores are a number you know at startup and can cap.

Thirty-two bytes

The record is fixed width, which is what makes a claim a single index bump rather than a variable-length reservation. Names are interned ids, not strings, for the same reason: a scope must cost a handful of stores, never a copy.

The write path

Six stores and one atomic add. No lock, no compare-and-swap loop, no allocation, no syscall, no branch on a queue being full.

The cursor only ever increases; it never wraps back. A slot index is claim % slots_per_ring, and the claim number doubles as the sequence stamp, so a consumer can always tell a slot's current occupant from the one that occupied it a lap ago.

Where the time actually goes

An earlier version of this post said the ring cost about ten nanoseconds an event and that "a good half of that is the clock read". The second half of that sentence was wrong, and wrong in the way benchmarks usually are: the benchmark pushed a pre-built event with a constant timestamp, so it never read the clock at all. Two things fall out of that table, and both are more interesting than the number I first reported.

The atomic claim is 4.14 ns, a quarter of a real scope. That is a much better case for rseq than the dismissal a few paragraphs down originally implied — it is not "one instruction", it is a lock-prefixed read-modify-write against a plain increment, and the ratio is twenty-four to one.

But the clock read is 9.37 ns, more than half. Optimising the atomic while leaving that untouched is the wrong order of work. clock_gettime through the vDSO already reads the timestamp counter internally; what costs the nine nanoseconds is the vDSO's own generality. Reading rdtscp directly and converting with the same calibration the kernel publishes is the larger prize, and it is the one I would take first.

Where the obvious design is unsound

The natural way to write this is a per-core single-producer ring: a thread reads its core id, and since only one thread runs on a core at a time, only one thread is ever writing to that core's ring. No atomic needed at all — a plain store into the next slot.

That reasoning is exactly right in the kernel and exactly wrong in userspace, and the difference is preemption.

What rseq is, since it is the real answer

Restartable sequences are a Linux mechanism, merged in 4.18, for exactly this problem: letting userspace run a short critical section that is guaranteed to have executed entirely on one CPU, without a lock and without a syscall.

You register a small structure with the kernel through the rseq syscall — glibc 2.35 and later does this for every thread automatically and exposes it as __rseq_abi. Inside it, the kernel keeps a field that always holds the id of the CPU the thread is currently on, updated on every migration. That alone is useful: reading your CPU id becomes a thread-local load instead of a sched_getcpu() call.

The clever part is the second half. You also register a critical section descriptor: a start address, an end address, and an abort address. While the thread's instruction pointer is inside that range, the kernel promises that if the thread is preempted or migrated, it will not simply resume where it left off — it will jump to the abort handler instead. So you write the sequence as "read the CPU id, compute the slot, store", and if anything interrupts you anywhere in the middle, you land in the abort path and start over. What you get is an atomic-free, lock-free critical section with true per-CPU exclusivity, which is precisely the guarantee the naive design assumed it already had.

It is what makes genuinely per-CPU userspace data structures possible, and it is why allocators like tcmalloc use it for their per-CPU caches. It needs the critical section written so it can be restarted from the top with no side effects, and on most architectures wants a hand-written assembly sequence with the abort handler placed by the linker behind a specific signature.

I first wrote that this was "a lot of machinery, and a hard dependency on one operating system, to save one instruction". The measurement above says the saving is 4.14 ns, a quarter of a scope, so "one instruction" was a bad way to put it. And the operating-system objection is weaker than it sounds for most of this port — the service is Linux-only throughout, tracepoints and uprobes and /proc and all.

It is not weak here, though, and the reason is worth stating because it is easy to miss: this is the one part of Orbit that does not run in Orbit. The producer is compiled into the profiled application, which may well be a game shipping on Windows. So a portable path has to exist regardless, and the question is not "rseq or the atomic" but "rseq and the atomic, chosen at compile time". That is a perfectly reasonable thing to build — it is just two write paths to keep correct instead of one, and the second one has to be there either way.

So the rings are multi-producer instead, and the slot is claimed with a relaxed fetch_add. Uncontended that is about twenty cycles; contended it is the one thing on a cache line that two cores are fighting over, which is why the per-core sharding still matters even though it is no longer a correctness argument. It stopped being a correctness argument and became a contention argument, and it is still worth having.

There is a test for this, and it is the kind worth writing: eight threads pushing to one ring, then a check that every producer's events all survived with a slot of their own. Replace the fetch_add with a plain increment and it fails immediately.

The one fence

The design brief said "no atomics, no CAS, no fences on the write path". Two of those survive. The third needs a qualification that costs nothing on the machine most people are reading this on, and one instruction elsewhere.

The payload stores can be plain. The store that publishes the slot cannot: without release ordering, the compiler or the processor may make the sequence stamp visible before the bytes it vouches for, and a consumer reads a slot the producer has not finished writing. On x86-64 the hardware does not reorder stores with other stores, so a release store compiles to an ordinary mov and the claim is literally true. On aarch64 it is one stlr. This codebase targets both, so the honest version of the claim is: no fences where the hardware gives them to you for free, and one instruction where it does not.

Drain, then merge

The consumer copies each ring's committed prefix out in one pass, then merges the snapshots. That split is the reason a slow consumer never stalls a producer: producers keep writing into the rings while the merge chews on a copy.

The merge itself is the textbook k-way merge — a min-heap over K cursors keyed by timestamp, pop the earliest, advance that cursor, push the new head, O(log K) per event. Nothing here is a linked list. It is a BinaryHeap over a flat Vec, a VecDeque per ring, and slices that are plain arrays; the "Rust hates linked lists" complaint is about pointer-chasing node allocation, and this design does none.

The horizon, and why an idle core nearly broke it

You cannot emit an event as soon as you see it. A ring you have not looked at yet might hold something older, and once you have emitted a later event you can never insert an earlier one in front of it. The rule is: hold every event until every ring has proven it cannot still produce something older. Call each ring's proof its frontier, and the horizon is the minimum across all of them.

Stated as "wait until every ring has produced something past it", that rule never terminates. Most cores are idle most of the time, and an idle core produces nothing, ever. The first version of this deadlocked on a machine with thirty-two cores and three busy threads.

The fix keeps the property without inventing an arbitrary window. A ring with nothing in flight cannot produce anything older than the moment you looked at it, because timestamps are read at write time. So its frontier is the drain timestamp, and the window for an idle ring is zero.

The bug that a question found

Everything above was written, tested and committed. Then came the question: if a thread migrates between entering a scope and leaving it, so the start lands in one ring and the stop in another, is the merge still valid?

The answer is yes, and it is worth saying why, because it is the part of the design that does the most work for the least cleverness. Starts and stops are matched by (tid, scope_id) — never by ring, never by adjacency, never by cross-core timestamp order. Depth comes from thread-local storage, which follows the thread across cores. The merge keys on timestamp alone and does not know or care which ring an event came from. Migration makes the sharding imperfect, which is a contention problem, not a correctness one.

But going to check that took me to the frontier calculation, which was wrong.

Multi-producer rings have a consequence I had written down and not followed through: claim order is not timestamp order. Two producers can read the clock in one order and claim slots in the other. Which means a ring can hold a committed event that is newer than a pending one sitting behind it:

The fix is the second atomic in the slot. A producer announces its timestamp immediately after claiming and before writing the payload, so a consumer that finds a slot in flight has an exact lower bound on what is still coming, and holds the stream just short of it instead of guessing from whatever happens to be committed behind it. That is the pending_ns field in the layout above, and the reason there are two atomics per slot rather than one.

The cost was one release store: 9.7 ns an event became 10.2. The test builds that interleaving deterministically, and I checked it in both directions — with the old rule it fails and prints the event it wrongly emitted; with the new one it passes. A test that has only ever been seen to pass is not evidence.

One residual case is not fixed, and I would rather say so than round it off. If a producer is descheduled inside the two instructions between the claim and the announcement, there is no sound lower bound available, so the stream holds where it is rather than guessing. That is a stall, not a reordering, and it clears on the next pass — but it is a stall, and pretending the window is zero would be a lie.

Why not the TSC

A timestamp counter read is faster than clock_gettime, and at ten nanoseconds an event the clock is a meaningful share of the cost. It is still the wrong choice here, and not for the usual reasons about invariant TSC or cross-socket skew.

Manual scopes have to appear on the same timeline as scheduling slices, thread states and sampled callstacks, all of which arrive from perf stamped with CLOCK_MONOTONIC. Two clocks means two timelines that cannot be interleaved, and a scope that cannot be lined up against the context switch that interrupted it has lost most of its value. The vDSO makes clock_gettime a function call rather than a syscall, which is what makes this affordable at all.

This is also the shape of a bug found earlier in this port, in a different module: a timestamp taken from a clock that counted from its own first call rather than absolute CLOCK_MONOTONIC. Everything downstream looked several decades out. Clocks are worth being pedantic about.

The reader assumes the writer is hostile

The segment is written by another process that may be buggy, mid-crash, or simply a different build. So the reader maps it read-only — a consumer must not be able to corrupt the process it is observing — and validates every field of the header against the mapped length before reading a single event: magic, version, record size, ring count in range, slot count a power of two, and the described layout actually fitting in the file.

The magic is stored last, with release ordering, so a reader that opens the segment while the writer is still initialising it sees "not initialised" and retries rather than mapping garbage at plausible-looking dimensions. Overflow is handled the same way: if a producer laps the consumer, the drain detects it from the sequence stamps, skips to the oldest slot still resident, and reports how many events were lost. Losing events under sustained overload is correct behaviour for a design whose first rule is that producers never wait. Lying about it would not be.

What is not built yet

  • The C API. None of this is reachable from an instrumented program yet. That is the ORBIT_SCOPE macro, the interned name table, and the thread-local depth counter and scope-id counter.
  • A second process. The shared-memory path is exercised by a writer and a reader in one process. Two processes is the next test, and the one that would catch a layout that only agrees with itself.
  • Service integration. Merged events need to become API_SCOPE events on the timeline, which is a small piece of work once the stream exists.
  • Nesting reconstruction. The design is settled — a map from (tid, scope_id) to the open start — but it is not written.
