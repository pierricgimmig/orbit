The First Few Bytes

Frida is Orbit's new default dynamic instrumentation engine. Getting a scope onto the timeline starts with a jump written over somebody else's instructions. Following that jump explains the trampolines, the shared manual API, the ARM support, and the functions we still cannot promise to instrument safely.

Implementation: Frida integration notes. Mechanics checked against Frida 17.17.0. Includes a runnable Linux x86-64 probe and its recorded results. Addresses in the explanatory diagrams are illustrative.

Select a function, press Record, and its calls become rectangles. It looks like the profiler has learned to observe something the program was already doing. In this implementation, the profiler has changed what the program does: its first instructions now take a detour, its return takes another, and both detours write events through Orbit's manual instrumentation API. The work is making those changes preserve the program's behavior closely enough that the rectangles mean what we think they mean.

The Rust service now defaults to Frida for dynamic instrumentation on Linux and macOS. Linux's existing uprobes are still selectable. This is also the point where manual and Frida scopes become one properly nested stream. Orbit owns the capture machinery; Frida owns injection and the instruction-level detours. That boundary buys us native Apple Silicon support without making a new AArch64 relocator a prerequisite.

Three pieces called Frida

Frida Core attaches to a running process and gets the agent into it. Gum is the native instrumentation library inside that process. Interceptor is the Gum facility we use to run callbacks at entry and return. Stalker, Frida's basic-block tracing engine, is a different facility and is not on this capture path. Frida also supports an embedded Gadget deployment, but Orbit currently uses attachment to an existing PID. See Frida's deployment modes.

The implementation pins the Python Frida package to 17.17.0. A JavaScript agent creates native CModule entry/leave callbacks, which call the injected Rust agent's lifecycle guard. That guard invokes the Orbit API. There is no per-call JSON message, Python callback, or script callback. There are still callback dispatch, timestamp, synchronization, and ring-write costs; native does not mean free. The concrete boundary is in agent.js and orbit-frida-agent.

A jump needs room

Suppose a function starts at address F. Gum allocates executable code for its detour, decodes enough complete instructions at F to make room for a redirect, and relocates those instructions into an invocation trampoline. It then replaces the original prefix with a jump. After the entry callback, the trampoline executes the displaced work and transfers control to F + N, the first untouched instruction.

On x86-64, a common redirect is a five-byte E9 rel32 jump. But five bytes of patch do not imply five bytes of displaced instructions. If the first instruction is six bytes long, all six must move. If instruction lengths are one, three, and four bytes, the prefix is eight bytes. Splitting the third instruction at byte five would leave its remaining bytes to be decoded as unrelated instructions.

Gum's pinned x86 interceptor backend tries to allocate nearby code so the signed 32-bit displacement can reach it: roughly two GiB in either direction. Its fallback reserves a sixteen-byte full-redirect budget. That is a backend budget, not a claim that every x86-64 hook is a sixteen-byte jump. Allocation, distance, the available prefix, and the decoded instructions all matter. A small function can be unhookable even when its address and symbols are perfectly correct.

Moving an instruction changes its meaning

Copying bytes is enough for some instructions. It is wrong for one that refers to data relative to its own instruction pointer. Consider the seven-byte x86-64 instruction mov rax, [rip + displacement]. RIP-relative addressing uses the address immediately after the instruction. At 0x1000, displacement 0x1ff9 refers to 0x3000:

old next PC + old displacement = data address
     0x1007 + 0x1ff9           = 0x3000

new displacement = data address − new next PC
          0x0ff9 = 0x3000      − 0x2007

Move the bytes unchanged to 0x2000 and the load reads 0x4000. That could fault. Worse, it could read valid memory and quietly return the wrong value. Relocation preserves the address being referenced, not the literal displacement encoded in the original instruction.

The x86 relocator adjusts the displacement when the new one fits. Out-of-range operands require instruction-specific expansions; some use scratch-register sequences. Relative calls and branches need their own treatment, and expanding a short branch can itself change the layout of the emitted code. Some conditional branches targeting instructions inside the relocated block are rewritten to local labels. It would be wrong to generalize that into “every internal branch is remapped”: the unconditional and conditional rewrite paths differ.

AArch64 makes instruction boundaries easier: instructions are four bytes long. It does not make relocation trivial. ADR, ADRP, literal loads, and relative branches derive addresses from where they execute. A page-relative ADRP followed by an ADD must still construct the original address after relocation. Conditional branches and test-bit branches have different reach from an unconditional B. The AArch64 relocator has separate rewrites for these instruction families.

The AArch64 interceptor prefers a sixteen-byte redirect when it can move that much code. With a shorter safe prefix it can try an eight-byte sequence or a four-byte branch to nearby code. The four-byte branch has roughly ±128 MiB reach; placement and an available scratch register constrain the other strategies. Fixed-width instructions eliminate one bookkeeping problem, not the need for a real code generator.

The jump the relocator cannot see

There are two different branch problems. A branch inside the prefix is among the instructions being moved, so the relocator gets a chance to rewrite it. A branch outside the prefix that jumps back into it is still executing at its original address. Relocating the prefix does nothing to that branch.

This is not just a hypothetical objection. The committed probe compiles three tiny assembly functions, attaches pinned Frida to a disposable child for each, and invokes it once after attachment. The Linux x86-64 result records the original and patched bytes as well as the process outcome:

FunctionUninstrumentedAfter Interceptor.attach
RIP-relative loadReturns 42Returns 42; one entry and one leave
Loop to F + 2Returns 3Attachment accepted; execution dies with SIGSEGV
Loop to FReturns 0Returns 0; three entries and three leaves

The last case is a separate failure of interpretation. Jumping to the exact entry executes the redirect again. It is not a recursive call: it pushes no new return address. In this probe Gum still reports three callback pairs for one call from C. A profiler counting those pairs as three source-level invocations would be wrong even though the function's result survived. These are observations of this pinned build and these bytes, not a promise about every allocation, backend, or loop shape. The reproducer uses simple JavaScript listeners to isolate Gum; it does not exercise Orbit's native event path.

Gum does have safety checks. In the default checked relocation policy, the AArch64 relocator can scan reachable forward code for direct branches into the proposed prefix and shrink the safe relocation length. Its forward scan starts with a 1,024-byte decode budget. It also inspects branches in the prefix. This is useful protection; it is not whole-program control-flow analysis. Indirect destinations, other entry points, and edges outside the analysis are harder. Its interior-target test also distinguishes an offset greater than zero from a jump to the exact entry. The x86 checks are different and accepted our failing example. See the pinned ARM64 relocation check and x86 relocation check.

Other troublesome cases follow the same principle: overlapping code, a hand-written secondary entry, a jump table reaching into the prefix, or a JIT changing the bytes after attachment. Symbol boundaries are useful metadata, not proof that every control-flow edge respects them. An accepted hook means Gum prepared a hook; it does not certify semantic equivalence for arbitrary machine code.

One return detour, many return instructions

Finding every ret and patching it would require discovering the function's entire control flow. Gum normally takes another route. At entry it saves the original caller continuation in its invocation bookkeeping and substitutes its leave trampoline as the return destination. A normal return reaches that trampoline, the leave listener runs, and Gum resumes the saved continuation. Multiple early-return instructions can all reach the same leave machinery.

The substitution is explicit in Gum's invocation entry/exit code. ABI preservation is more than saving general-purpose registers: stack alignment, flags, floating-point state, return values, and architecture-specific control-flow protections matter. The x86 backend has explicit CET shadow-stack handling. The ARM64 backend has special treatment for some instructions that read LR. These are reasons to reuse a mature backend, not grounds for promising that every return-address-sensitive function or mitigation configuration works.

A tail jump does not establish a new return in the way a call does; the original invocation may finish only when its tail callee returns. An exception or longjmp may bypass a normal return altogether. Orbit does not infer language unwinding from Gum callbacks. Such a span can remain open and affect later nesting until the capture ends. A function that inspects its own return address, a custom unwinder, and a continuation-switching runtime all deserve targeted tests.

One API, not two depth counters

The useful integration detail is what the listeners do. On entry, the native callback gets a handle from orbit_start_dynamic and keeps that handle in Gum's per-invocation storage. On leave it passes the handle to orbit_stop. Manual instrumentation uses the same API instance, thread identity, TLS handle allocator, and shared ring. The service reconstructs synchronous nesting from the combined start/stop stream. There is no shared “depth TLS counter” to synchronize: depth is computed on the reader side.

Calling a second copy of a statically linked SDK would not achieve this. Each copy could own separate TLS and producer state. Instead, orbit_init publishes a versioned DynamicApiV1 function-pointer descriptor in reserved shared-header bytes. The injected agent discovers the already-running API through that descriptor, even when the application's API symbols are stripped. A producer-held file lease guards against reusing stale addresses after exit or exec. The descriptor is process-local discovery, not an RPC interface whose pointers another process may call.

An application without the SDK uses the injected agent's bundled API. An application with its own SDK must initialize it before attachment. Loading a second SDK later is unsupported. An older initialized SDK without this discovery contract fails attachment rather than having its segment replaced. Fork-child handling disables inherited instrumentation before it touches inherited state; the child must exec before instrumentation resumes. These rules belong to the API's lifetime contract, not to instruction relocation.

Provenance travels with the scope. Dynamic starts set bit 3 of the existing scope-event flags byte. Completed live records use bit 7 of the metadata byte, leaving the low bits for color mode. Capture exports preserve metadata in an optional flags column; older files default it to zero. The existing packed live encoding omits that byte, so batches with metadata use the existing raw encoding. We kept event sizes stable, at the cost of giving up that packing for those batches.

The capture-private Frida mapping holds a lease and completed-call counter, not another scope stream. A read lock protects callbacks against teardown; a generation prevents an old return from writing into a new capture. Stop detaches Frida before the ordinary scope source's final drain. Open scopes are clipped to capture end, just like manual ones. Ring loss and the reader's eight-bit depth limit remain real limits. Sharing a stream fixes the competing-hierarchies problem; it cannot reconstruct events that never arrived.

Installing the patch is another concurrency problem

Building correct trampoline bytes is only preparation. A running target may have other threads executing the code, or calls already past the entry point. Code pages have permissions, instruction caches may need synchronization, and a multi-byte write is not automatically an atomic replacement of the whole prefix. A four-byte instruction set does not make every multi-instruction patch atomic either.

Orbit delegates patch publication and executable-code allocation to Gum's interceptor transactions and platform memory-patching machinery. Gum also tracks trampoline use before reclaiming retired contexts. That is a substantial part of the library's value. It should not be summarized as “every thread always stops” or “patching cannot race”: the mechanism depends on the backend and platform. See the transaction and context-lifetime implementation.

A call already inside the original body when we attach has missed our entry. A call still running when we stop may never produce a completed span within the capture. Module unloading, other hookers writing the same entry, and self-modifying code complicate ownership further. The normal smoke test deliberately waits until hooks are armed before releasing the target; it does not settle those boundary cases.

The instruction set and the operating system are separate axes

Intel Macs use the x86-64 relocation machinery. Apple Silicon uses AArch64. Linux can use either architecture, and Gum also supports Windows. None of those facts alone establishes that Orbit's packaging, process discovery, symbols, shared-memory transport, and permissions work on every combination.

On Linux, attaching is subject to ptrace/Yama policy and other process-access checks. Gum's native callbacks run in user space; this is a different event path from kernel uprobes. The injected library must match the target architecture and be readable by it. The target must also be able to map the capture file. The service does not silently fall back to uprobes if Frida fails: changing engines would change the measurement without the user choosing it.

On macOS, resolving functions is itself an attach operation. The integration translates live Mach-O addresses using the correct architecture slice, segment layout, and ASLR slide. It prefers public function names over local assembler labels at the same address, because selecting ltmp0 instead of the real function was a practical bug, not a theoretical one. Shared-cache images can still lack usable symbols, and live Mach-O disassembly is separate future work.

Permission to obtain a task port and permission to load or execute the injected code are separate concerns. Apple's runtime protections restrict access to protected processes even for root. Hardened runtime, library validation, and signing also matter. The initial supported target is a development application. Our hosted Mac tests run collector and target as root to avoid interactive authorization prompts; they do not validate ordinary-user attachment to arbitrary signed software. DTrace is not a universal escape hatch: SIP also restricts its access to protected processes.

On Windows, the existence of Gum's backend saves an instruction-engine port, but not an Orbit service port. PE/module discovery, symbols, shared mappings, thread IDs, clocks, and agent distribution still need Windows work. The Windows x64 ABI differs from the System V ABI used on Linux, including its shadow-space convention. Process access rights and Control Flow Guard are additional concerns. Likewise, ARM pointer authentication or branch-target protection and x86 CET require backend-specific handling; “supports ARM” is not a blanket assertion about every OS policy or mitigation combination.

Why this engine, and what the others buy

There are several ways to get an entry timestamp. The harder requirement is getting useful entry and exit events on Linux and both Mac architectures, while reusing the same manual scope producer.

ApproachWhat it buysWhat remains

The kernel documents uprobes and return probes; Microsoft's Detours overview describes its trampoline design; LLVM documents XRay's compiler-inserted instrumentation. These are different deployment and observability tradeoffs, not a throughput ranking. This change contains no benchmark establishing that Gum is faster than the retained backend for a particular workload.

For a concrete comparison, the classic x86 uprobe path replaces the probed instruction's first byte with a breakpoint. The trap enters the kernel, which handles the probe and arranges for the displaced instruction's effect, often through execution out of line with fixups. A return probe also redirects the return continuation through kernel-managed machinery. That avoids needing Gum's multi-byte entry-jump prefix, but does not eliminate instruction handling or return-address changes. eBPF can process the probe in the kernel; it does not make the probe site cease to be a probe. These mechanics are visible in the Linux 6.12 x86 implementation and generic uprobe code; later kernels can change the implementation.

Loader interposition has a smaller remit: LD_PRELOAD changes dynamic symbol resolution. A direct internal call that never asks the loader for a symbol will not pass through that wrapper. It is useful for selected library boundaries, but does not replace selecting arbitrary function addresses in Orbit.

Writing our own Rust relocator is possible. A trustworthy replacement would also need near-code allocation, ABI-preserving stubs, safe publication, instruction-cache handling, return bookkeeping, mitigation support, and a large adversarial test corpus across architectures. Rust can improve ownership and lifetime reasoning around those pieces; it does not make an unseen branch into patched bytes safe. Reusing Gum lets Orbit spend that effort on capture correctness. A future direct native binding could change packaging without requiring us to rewrite the engine. Today's Python/Core packaging is not static Gum linkage into the Rust service.

A correct span is not a transparent callstack

Linux perf_event_open sampling can keep running while Frida instruments a function. It can sample a PC in the original body, in a relocated instruction, or in entry/leave machinery. A generated trampoline may lack the unwind metadata the external unwinder expects. More subtly, a sample deep inside the original body can still encounter the substituted return continuation while walking its callers.

Frame pointers do not universally fix this: a frame chain can still contain a return address belonging to Gum. DWARF unwinding is not a universal fix either: the unwinder needs rules for the actual generated code and its saved state. Gum has an invocation-stack translation helper that knows original return addresses inside the process. A separate perf unwinder does not automatically consult that bookkeeping. Orbit currently implements no trampoline-aware callstack repair.

So it is reasonable to collect samples and spans together, but sampled stacks through an instrumented call need validation before being treated as faithful. Uretprobes have their own return-interception machinery and should be checked separately; changing the engine does not by itself prove stack fidelity. A future repair mechanism must work at the sample's time, not consult mutable per-thread state later and assume it describes an older stack.

There is another distinction the timeline cannot hide: a scope duration is elapsed wall time between instrumentation events. It includes preemption and blocking, and the measurement perturbs the code. Entry and leave timestamps also sit inside the detour, not exactly on the original call and return boundaries. Native callbacks still take locks and write shared memory. For very short functions, the instrumentation can dominate the work being measured.

Finally, a symbol is not necessarily a source-level function invocation. Inlining removes entries, identical-code folding can give several names one address, and thunks or tail calls change the relation between machine calls and source calls. The loop-to-entry experiment is an especially small example of why “one callback pair” and “one source call” are different claims.

What has actually been checked

The integration's native smoke test uses a target with known work: three threads, 30 outer calls, 60 middle calls, and 180 inner calls per capture. That gives exactly 270 dynamic spans. Manual regions alternate with dynamic ones across seven nesting levels, and async regions must not enter that hierarchy. The checker verifies counts, provenance, containment, repeated capture, fork isolation, and target survival. Separate cases cover a target without the SDK and an SDK whose API symbols are stripped.

The native CI run passed on Linux x86-64, Apple Silicon, and Intel macOS for integration revision b3fb896b4, before the final rebase. That is useful platform evidence with the root-on-Mac qualification above. ARM Linux runtime and Rosetta validation remain pending. These tests do not certify arbitrary prologues, attach in the middle of a call, exception unwinding, sampled stacks, or every control-flow protection mode.

The three-function relocation experiment in this post answers a different question: what happens to these exact bytes under pinned Gum? It successfully relocated a RIP-relative load, demonstrated an accepted hook that crashes, and demonstrated entry callbacks counting loop iterations. It is intentionally small and is not an Orbit end-to-end test or a performance benchmark. To reproduce it on Linux x86-64:

python3 -m venv /tmp/orbit-prefix-venv
/tmp/orbit-prefix-venv/bin/pip install frida==17.17.0
/tmp/orbit-prefix-venv/bin/python docs/blog/experiments/frida-prefix.py

Each case uses a disposable child and disables its core dumps. The JSON includes compiler, kernel, architecture, patch bytes, results, and callback counts where the child survived. More relocation tests should include incoming indirect branches, tiny functions, tail transfers, unusual prologues, and real mitigation-enabled binaries. More profiler tests should measure overhead and inspect simultaneous sample stacks. Those are separate axes of correctness.

Using it now

On Linux, the packaging helper builds the agent and installs the pinned runtime beside the service:

./tools/frida/build.sh
./dist/frida/orbit-service --host 127.0.0.1 --serve 3000

On macOS, run ./build-service-macos.sh; --universal builds both native architectures for the service, manual API, and agent. The packaged Python environment belongs to the build host and should be recreated on a different machine using the runtime-only helper. Follow the build and runtime notes for prerequisites and development overrides. A Cargo-only service build does not install Frida. Ordinary manual captures do not need Python or Frida at all.

Select a running development process, load its functions, choose functions, and record. The current selection limit is sixteen functions; start with meaningful outer work rather than every tiny helper. If manual instrumentation is linked into the target, initialize its updated SDK before attaching. Linux users can explicitly select Uprobes to retain the old engine.

The next useful work is making the boundary easier to assess: clearer rejection diagnostics, adversarial relocation fixtures, overhead measurements, and tested callstack behavior. The detour is only the first part. What matters to Orbit is whether the event stream still describes the program the user meant to measure.
