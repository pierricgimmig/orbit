The Hook That Would Not Arm

Dynamic instrumentation, driven from the web UI: type a function name, tick it, record, and watch its calls appear as spans. Everything works except the part that needs a capability this machine could not grant.

A profiler that only samples tells you where time tends to go. Dynamic instrumentation tells you what actually happened: this function, this call, these nanoseconds. Orbit has always had both, and the Rust port had neither half of the second one wired to the UI. Wiring it took an afternoon. Proving it took longer than that, and then stopped short.

The half that already existed

The pleasant surprise was that the viewer already spoke the entire protocol. Its capture strip has a hook picker: it asks the service to load symbols, polls until they are ready, searches function names as you type, and puts the ids you tick into the capture request alongside a dynamic_instrumentation_method. All of it was written when the viewer was talking to the C++ service.

What the Rust service answered was three stubs. load_symbols returned "not implemented in the Rust service yet"; the status endpoint reported unavailable; the search returned an empty list. So the picker rendered, greyed out, forever waiting for symbols that were never going to arrive. The work was entirely on the service side, which is a good position to be in: the contract was already fixed, and there was nothing to design.

The one part that is not symbolization

Indexing functions is nearly the same job the sampler already does — read /proc/<pid>/maps, load each mapped ELF's symbol table — except keyed by name instead of by address. One thing is genuinely different, and it is the thing worth being careful about.

A uprobe is not placed at a virtual address. It is placed at a byte offset into a file: the kernel finds the inode, and every process that maps that file gets the breakpoint. So a function's ELF symbol address has to be walked back through whichever PT_LOAD segment contains it. For the test target's executable segment that arithmetic is a no-op, because the linker put p_offset and p_vaddr at the same value:

The second segment shows both reasons not to assume. Its file offset and its virtual address differ by 0x1000. And its size in memory (0x288) exceeds its size in the file (0x270) — that tail is .bss, which exists when the program runs but has no bytes in the file at all. An address landing there has no file offset, and asking for one has to return nothing rather than a plausible-looking number.

The reason to spend a tested function on twelve lines of arithmetic is the failure mode. Get this wrong and nothing complains: the kernel accepts the offset, writes a breakpoint into the middle of some unrelated instruction, and the target either produces nonsense or crashes far away from the mistake. There is no error to read. So the conversion is its own function with its own tests, including one that pins the .bss tail to None.

Per task, not per CPU

Orbit's C++ opens uprobes on every CPU in the cpuset. That has a known consequence, documented in this port a day earlier while chasing a different question: when a thread migrates mid-probe, one logical hit can surface in two per-CPU ring buffers, and UprobesUnwindingVisitor carries a (sp, ip, cpu) filter to throw the second one away. The underlying mechanism appears to be the execute-out-of-line preemption window, though that part remains a strong inference rather than a confirmed kernel bug.

The Rust collector opens probes per task instead, with inherit set so threads created later are covered too. A thread has exactly one buffer wherever it runs, so the duplicate cannot be constructed, and the filter did not need to be ported. The cost is file descriptors — two per hook per thread — which is why the number of hooks is capped at sixteen rather than left open.

Trading one problem for another is the honest description, though, because per-task probes create a different one. Entry and exit now live on separate rings, and there is no ordering between two rings drained microseconds apart. A naive loop will hand you a function's exit before its entry and then compute a duration by subtracting a timestamp that has not arrived yet. So hits are buffered and paired in timestamp order behind a 100 ms horizon — the same delayed-ordering idea the collector's main loop uses, in miniature. Two of the unit tests exist purely to pin that: one feeds the exit first, one checks that nothing is paired before the window has passed.

The wall

Then it did not work.

The reflex here is to reach for perf_event_paranoid, which is the knob that governs almost everything else in this port. It was already at -1, the most permissive setting there is, and it made no difference — because for this PMU it is not consulted. In the kernel, perf_uprobe_event_init checks perfmon_capable() and returns -EACCES before perf_event_paranoid enters the picture at all. Tracing PMUs are gated on the capability, full stop. On a machine with no sudo available, there is no arrangement of settings that opens a uprobe.

So the feature is unproven in the way that matters: no probe has been observed to fire, and no span produced by one has been drawn. That is the honest state of it.

What a refusal is still evidence of

It is not nothing, though, and it is worth being precise about which part is established. The uprobe PMU has no fixed type number — the kernel assigns it at boot and publishes it in sysfs, here as 9. A wrong type number comes back ENODEV. A malformed perf_event_attr comes back EINVAL. What came back was EACCES, which is the answer from inside the uprobe PMU's own initializer.

That establishes routing and rejects two whole classes of mistake. It says nothing whatsoever about whether the offset lands on an instruction boundary, or whether the pairing works against real kernel timestamps. There is now a test that asserts exactly this much and no more: if the process happens to be privileged it checks that probes armed, and otherwise it checks that the refusal was EACCES rather than something that would indicate a bad attr. A test that claims less than the feature does is more useful than one that pretends.

Making the failure visible

The worse outcome than a hook that does not arm is a hook that does not arm quietly. From the UI, an unarmed probe and a function that simply never ran look identical: an empty track. Someone would reasonably conclude the profiler was broken, or that their function was dead code.

So the arming outcome now travels back to the browser. The service carries a one-line instrumentation status, /api/status reports it, and the viewer prints it under the hook picker — muted when functions were armed, amber when they were not:

The omission is deliberate. Every other permissions message in this service mentions perf_event_paranoid, because for every other feature it is the answer. Mentioning it here would send a reader down a dead end for an afternoon, which is worse than saying less.

What is still missing

  • User-space trampolines. The viewer offers two methods, and Orbit's default is the trampoline-based one, which is far cheaper than a uprobe because it does not trap into the kernel per call. The relocation and placement machinery is ported; installing it into a live process is not. A request for that method is honoured through uprobes and says so in the log rather than silently substituting.
  • Probes firing. Everything above the syscall is tested; the syscall itself is blocked here. This wants one run on a machine with CAP_PERFMON before anyone calls it working.
  • Arguments and return values. The pairing carries slots for both, because the ported FunctionCallManager has them. Nothing fills them yet.

A note on stopping here

The tempting move at this point is to write "dynamic instrumentation: done" and let the next person discover the gap. The whole value of keeping these numbers in a file is that it makes that move harder. docs/blog/metrics/phase-8-dynamic-instrumentation.txt has the sysfs values, the JSON the endpoints returned, the program headers of the target so the offset arithmetic is checkable by hand, and a closing section headed "Not measured, and why". A feature that is nine-tenths verified is worth more than one described as finished, as long as the missing tenth is named.
