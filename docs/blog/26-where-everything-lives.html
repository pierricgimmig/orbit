Orbit C++ → Rust · Post 26

Where Everything Lives

For two months the repository was two profilers sharing one tree: eighty-two C++ directories under src/, twenty-four vendored libraries, a Bazel graph that stitched the Rust in as static archives, and the Rust itself tucked into rust/ as if it were the guest. The C++ is gone and the Rust is at the root. This post is the map: one workspace, thirty-one crates, four directories, and the paths between them.

On the rust-canonical branch, PR #118. Every count below is git ls-files on that branch; the crate graph is read out of the Cargo.toml path dependencies.

A repository's layout is a claim about what the project is. Until this week the claim was "a C++ profiler with a Rust port growing inside it": src/ held the Qt application and the C++ service, third_party/ held LLVM, Qt and libunwindstack, MODULE.bazel was 1.9 MB of lockfile, and the Rust lived in a side directory whose crates were linked into OrbitService through a row of -ffi adapters. Post 13 measured the moment the Rust service overtook the C++ one; posts 14 through 25 never touched a C++ file again. The tree just had not caught up.

The cleanup is simple to describe and tedious to do: delete everything the C++ build owned, move the Rust from its side directory to the root, merge its six Cargo workspaces into one, and follow every path. What follows is the result, drawn.

The top level

A Cargo workspace root, and four directories beside it. The files are what any Rust repository has, Cargo.toml, Cargo.lock and the toolchain pin, plus run.sh, which builds the service and opens the viewer, and the usual README, LICENSE and .gitignore. The directories are where the counting starts.

crates/: the service, in layers

Twenty-four crates on the service side, and the number is the port's history rather than a design: each phase of the port produced the crate that replaced one C++ library, and the crates kept their boundaries after the C++ left. That turns out to be a reasonable layering. Read from the bottom, each row depends only on rows below it.

Two crates are worth singling out because they produce more than a library. orbit-api builds as an rlib, a static library and a shared library at once: liborbit_api.so is what orbit.h loads at run time, and the Python package beside it talks to the same shared object through ctypes. orbit-service is the binary, and its python/ directory is the orbit-profiler wheel that wraps it. Two files that used to sit loose at the root of rust/, included by #[path] from the two Frida crates, now have crates to live in: the devkit link logic is orbit-frida-build, a build-dependency of the agent and the helper, and the setup-only timing is a module of orbit-frida-transport.

crates/orbit-live-*: the web stuff

The viewer used to be src/OrbitLiveViewer, a PascalCase name under the C++ tree because it was born as the C++ service's web front end and linked into it through orbit-live-ffi. That crate is gone, and the seven that remain sit in crates/ with everything else, the pack beside the viewer crate in crates/orbit-live-viewer/viewer-dist. It is the one part of the tree with a build step that is not cargo build, and the diagram is mostly about that step.

The server has a main.rs of its own, which serves the viewer with a demo producer and no capture stack; that is the fastest way to work on the front end. The real thing is the service: it installs orbit_api::scope into the server's Instrument hook at start-up, which is how the viewer's own WebSocket sends show up as scopes in a capture of the service.

One workspace, where there were six

A canonical Rust repository has one Cargo.toml at its root, one crates/, one lockfile and one target/. Until this week this one had six workspaces and seven lockfiles, and every manifest explained why in the same words: Bazel's crate_universe spliced rust/ into a temporary directory to generate its dependency graph, and a path dependency that left rust/ broke every Bazel build. So orbit-service, which depends on the viewer's server, had to be its own workspace. So did orbit-capture. So did the viewer, three times over. The other reason given, keeping eframe out of the service's lockfile, was never one Cargo needed: feature resolution is per build graph, so cargo build -p orbit-service never compiles eframe whether or not the viewer shares its workspace.

What the merge took: one [workspace] listing the 31 crates, one lockfile built from the seven, one toolchain pin, a [profile.wasm] so the pack keeps the plain release settings it had in its own workspace, and every --manifest-path in a script or a workflow turned into a -p. The per-crate target/ directories went with it; everything builds into the one at the root, including the Frida devkits that tools/frida/devkits.sh fetches into it.

docs/: the manual, the log, and the site they become

docs/manual/ is the user-facing reference, twelve Markdown pages from capture.md to troubleshooting.md. docs/blog/ is this log: twenty-six self-contained HTML posts, the metrics/ directory of sixty-eight committed snapshots that every number in them comes from, and two captured streams the front page replays. Four longer essays sit at the top of docs/ next to the build and release notes. The plans, briefs and reviews written while the work was open, the Windows handoff brief, the cross-platform plan, the sampling-viewer plan, the uprobe and instrumentation analyses, live in docs/design/, where the code comments that cite them still find them and where a reader of the manual does not have to step over them.

Notice what none of them run: cargo test --workspace in rust/. The crates CI tests are the ones a platform job needs, and the rest are run by hand. That gap showed itself during this cleanup, when the full workspace test suite turned out to include a self-sampling unwinder test with no bound on the records it kept; on this machine it reached 70 GB before the OOM killer stepped in. It is bounded now, 4,000 records or five seconds, and runs in under a second. A workspace-wide test job is the obvious next addition.

What is not in the tree, and where it went

The C++ application, its Bazel build, third_party/, the Qt icons, the distro-matrix CI and the differential tools that held the two implementations against each other are on the cpp branch, at the last commit before the first Rust one. Every pointer in the docs that used to name a C++ file as "the specification this test mirrors" now says so with the branch beside it. The sixteen C and C++ files that stayed are the public header and its Unreal copy, three thin shims over the Frida devkits, the C targets the tests profile, the two example programs, six fixture sources and one blog experiment. None of them is Orbit's old code; all of them are the Rust profiler's.

Not in the tree either, by design: target/ directories, the built /site, the wheels' staged binaries, and the Frida devkits, which tools/frida fetches and verifies rather than vendors.

The short version. One Cargo workspace at the root. crates/ holds the service in layers and the seven viewer crates with the committed pack the service embeds; tools/ tests, builds and ships it; docs/ explains it and becomes the site, with the working notes in docs/design/. Nothing of the previous life is left in the tree but the blog that tells it.
