What the Agents Are Doing

Several coding agents work a queue at once. Their notes say what they meant to do; their own transcripts say what they did, to the second, without anyone asking. A design for getting both onto one live timeline, and a prototype that already draws the second half.

The queue is q; the timeline is Orbit. The prototype is tools/agents/transcript_to_orbit.py on this branch. Everything measured below is a real session of the agent that wrote this post.

With one agent you watch the terminal. With four, on four tasks, you watch q top: a table of statuses and a percent each agent last reported. That tells you where the work stands. It does not tell you what an agent is doing right now, whether the thing it has been doing for six minutes is a build or a stall, or where its last hour actually went. This post is about closing that gap with what the agents already produce.

What is already there

Three pieces exist today, and the design is mostly about lining them up.

The task log. Every q task carries an append-only, timestamped, actor-attributed log. The queue writes the state changes itself (task_claimed with the agent id, task_started with the branch, task_completed with the summary). The agent adds q log ID "…" notes, --progress 40, and artifacts; --attach report=PATH stores a report's text in the database so it outlives the file. This is the agent's intent: what it says it is about to do, what it found, what it decided.

The bridge. q orbit (q PR #26) tails that log and posts it to a running orbit-service. Each task is a process, each agent that claims it is a thread of that process, status phases are spans, notes and heartbeats are marks, progress is a value lane, and a note written [explore] @begin … opens a span on a sub-thread named explore. q exec -- cargo test (PR #27) adds a span per process the agent launches, with its exit code as a mark. Orbit's side is POST /api/events (#87, merged): a batch of named processes, threads, spans, instants and values, stamped on the wall clock and converted to the capture clock by the service, so a producer on another machine works as is.

Orbit itself. Attached to a build or a test run the agent launched, it draws that process the way it draws anything: samples, scheduling, scopes.

What all three have in common is that the agent has to do something for them: write a note, wrap a command in q exec, attach a profiler. That is the right design for intent. It is the wrong one for the record of what happened, because the record already exists.

What an agent leaves behind without being asked

Claude Code writes every session to ~/.claude/projects/<cwd>/<session>.jsonl, one JSON record per line, as it goes. The session that produced this post is 1,647 lines and 10 MB, and the records that matter are few:

One more thing falls out of the timestamps. Between a tool result and the next assistant message nothing runs but the model. That gap is the model's own time, generating, and it is measurable per turn without any instrumentation of the model at all.

Codex does the same in ~/.codex/sessions/: response_item records of type custom_tool_call and custom_tool_call_output, reasoning items, token_count events, 7,837 lines in the one session on this machine. The shape differs, the content is the same, and a second reader for it is a mapping, not a design.

And Claude Code's hooks (PreToolUse, PostToolUse, Stop, SubagentStop) hand a script JSON on stdin with the session_id, the transcript_path, the tool name and its input. They are the push form of the same record. Their most useful field here is the transcript path, because it is the one thing a queue cannot discover on its own.

The design: three lanes, one timeline

The join is the only new piece of queue design. Today q orbit draws an agent thread from the log alone, and the tailer draws a session from the transcript alone; they do not know about each other. They should, and the key is the transcript path: an agent that claims a task tells the queue where its transcript is, and the bridge tails it under that agent's thread.

# proposed: the transcript travels with the claim
q start 29 --claim-token $T --branch agent/task-29 --transcript "$CLAUDE_TRANSCRIPT"

# or, with no cooperation from the agent at all, a SessionStart / PreToolUse hook
# that reads transcript_path from stdin and writes it next to the task id it already keeps:
jq -r .transcript_path > .claude/q-transcript   # q orbit picks it up from the claim's cwd

With that one field, q orbit becomes the tailer too: the agent's thread under the task's process shows claimed, then in_progress, then inside it every tool call as it happens, the model's turns between them, its sub-agents on their own threads, and its notes as marks laid over the spans that were running when it wrote them. Intent on top of action, same thread, same clock. A note that says "running the e2e suite" followed by a span Bash: run the e2e suite that is still open eleven minutes later is a stall you can see. A model span that runs long before every reply is a context that has grown too big, and the context tokens lane says so next to it.

The prototype

tools/agents/transcript_to_orbit.py is the second lane on its own: about 250 lines, no dependencies, and no change to the agent. It follows the newest transcript (or one you name, or every one touched in the last hour with --all), keeps a file offset and a partial line, and posts a batch to /api/events every second. --once replays and exits; --since 45m replays only recent history; --summary prints where the time went.

That last line is the prototype noticing itself: the tool call that ran it had no result yet when it read the file. Below is the last three quarters of an hour of the same session, as the viewer draws it. Red spans are the model; green and blue are tool calls, named by the description the agent gave each command; the two lanes are output tokens per reply and the size of the context.

The mapping in full: the process is the session, named for its directory and short id; agent is the main conversation and each sidechain root gets a thread; a span per tool call from tool_use to its tool_result, nested by the number of calls still open on that thread; a model span from every result (or prompt) to the next assistant message; marks for prompts, replies and the moment a call starts (so a call with no result yet is still visible); output tokens and context tokens lanes from usage. What leaves the machine is names, timestamps and counts. Command output, file contents and prompt bodies stay in the transcript; the one string that travels is the agent's own description of a command, cut at sixty characters.

Two agents on the same codebase, opposite shapes. One spends three quarters of its working time generating and runs many short commands; the other runs a third as many commands and waits on them for most of its time: builds, and polling a pull request's checks. Neither shape is visible from q top, and the difference is the difference between an agent that needs a faster model and one that needs a faster build. The transcript already knew.

Honest note

"Model time" is the gap between a result and the next assistant record, which also contains the harness's own overhead and the streaming of the reply. It is an upper bound on generation and a fair measure of "the agent was thinking, not the tool". Idle time while a session waits for a person is excluded, because a prompt resets the clock.

What is proven, and what is a proposal

Proven: the prototype reads real Claude Code transcripts, this session's and a sibling's, and a service built from Orbit's main accepted every record it posted (1,419 and 358 in the two runs above, none dropped). The capture embedded above is the service's own export of that run. The summary numbers are computed from the same records.

A proposal: the transcript path on the claim and q orbit tailing it under the agent's thread. A mapping, not yet written: Codex rollouts. Untested: sub-agent threads, because neither session here spawned one, and the hook recipe inside a live session. Remote agents need the tailer where the transcript is, posting to a central Orbit, which the wall-clock stamp already allows.
