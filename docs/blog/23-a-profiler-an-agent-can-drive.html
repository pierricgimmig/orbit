A Profiler an Agent Can Drive

Orbit grew a closed optimize-and-profile loop you point at any external project through a config file — build it, benchmark it, profile it with Orbit, propose a change, and accept it only if a statistical gate says the win is real. The loop is exposed over MCP, so a coding agent can run the whole cycle without a human in the seat. This post walks the mechanism end to end, with the MCP wiring drawn out in full, and shows it profiling Stockfish.

The tooling described here is on the Rust branch, in tools/optimize-loop/, and has not yet been merged into main; the target is a .toml/.json/.yaml file, never a submodule. Orbit does not vendor Stockfish or any other target.

A profiler tells you where the time goes. The harder half of optimization is the loop around it: build, measure, read the profile, change something, rebuild, measure again, and decide honestly whether the number moved or whether you fooled yourself with noise. That loop is mechanical, and mechanical work is what an agent is good at — provided the tool it drives is safe to hand a model, and honest about what it measured. This change makes Orbit that tool.

What it is

Point it at a project with a small config: where to build, how to bench (with a line the tool can parse into a number), an optional correctness check, and a capture command — a child process Orbit attaches to. There is no target-specific code and nothing vendored; Stockfish is just one config among many, cloned out of band and left alone.

# stockfish.toml — a target, not a submodule
project = "/home/you/git/stockfish"

[build]  command = ["make", "-C", "src", "-j", "build", "ARCH=native"]
[bench]  command = ["./sf-bench.sh"]        # prints: ORBIT_METRIC throughput=<nps>
                                            #         ORBIT_FINGERPRINT <nodes>
[capture] command = ["./sf-capture.sh"]     # a multi-second run Orbit samples

Two lines in the bench output carry the whole gate. ORBIT_METRIC is the number to improve (Stockfish nodes/second). ORBIT_FINGERPRINT is a value that must not change — for a chess engine, the node count of a fixed search, which is deterministic: if a “speedup” changes it, the engine now computes something different and the win is a bug.

The loop

One iteration is a straight line with a fork at the end. The config feeds every command; Orbit does the capture; the gate makes the call; a rejected change is put back exactly as it was.

Capture is Orbit, only Orbit

The capture step launches the workload as a child and attaches Orbit to its PID — first serve mode (the same HTTP/WebSocket service the live viewer uses: load symbols, capture/start, then read /api/sampling/report), and if that records nothing, Orbit’s file mode (--pid --out, one leader thread sampled to a .pod). An earlier draft also had a perf backend as a fallback. It is gone: perf did nothing Orbit does not already do, and this loop exists to exercise Orbit. The point was never to benchmark a chess engine — it was to prove Orbit’s own capture on a large, real, multi-threaded C++ program, and it does.

Honest note

The README long warned that serve mode on some Linux VMs opens rings and records 0 callstack samples. That is real, and the loop refuses to invent a win from an empty profile. But on Stockfish, a heavy native workload at perf_event_paranoid = -1, serve mode captured 12,901 samples and the hotspots were exactly what you would expect — the caveat was too pessimistic for this class of target, and the tool now says so.

The MCP part, in full

This is the piece worth understanding. MCP — the Model Context Protocol — is how a language model calls tools that live outside it. The model does not import Python or run shell; it speaks a small JSON-RPC dialect to a server that exposes named tools, and the server does the work. Orbit ships one such server: tools/optimize-loop/mcp/server.py. It is a plain process that reads JSON-RPC 2.0 requests on stdin and writes replies on stdout — no framework, no network port.

Two things make this safe to hand an agent. First, the server holds no secrets and calls no model: it is pure mechanism — run a build, read a report, edit a file — and the intelligence stays on the driver side of the stdio line. Second, optimize_apply_patch is sandboxed: it writes only inside the configured project, cannot escape it or touch .git, defaults to a dry run, and never commits, pushes, or force-pushes. The worst an agent can do is edit a file the loop then reverts.

The seven tools cover the whole cycle. optimize_run_suite builds, benches and captures. optimize_get_summary and optimize_inspect_hotspots read the last result. optimize_apply_patch proposes an edit, optimize_rebuild compiles it, optimize_rerun_compare re-measures against the baseline, and optimize_run_loop runs the entire baseline→propose→rebuild→gate→revert sequence in one call.

One call, start to finish

Speaking MCP is three messages: a handshake, a catalogue, and a call. The reply to a tool call wraps the tool’s JSON result as text content — a small wart of the protocol, but a stable one.

The gate says yes only when it should

The reason a loop like this is trustworthy at all is the gate. A benchmark wobbles; the job of the gate is to reject a change unless the improvement is bigger than the wobble and the program still computes the same thing. Three conditions, all required.

Pointed at Stockfish

Cloned to ~/git/stockfish, built with make ARCH=native, and driven entirely through the MCP server, the loop profiled it and returned a hotspot table that reads like the engine’s own architecture:

samples: 12,901  (orbit serve mode)
  35.8%  NNUE ...apply_combined
   9.3%  NNUE NetworkArchitecture::propagate
   7.3%  Search::Worker::search<PV>
   6.7%  MovePicker::next_move
   5.7%  NNUE update_accumulator_refresh

Then the closed loop ran, also through MCP: baseline 1,392,411 nodes/sec, a labeled no-op edit, a rebuild, and a re-bench at 1,378,550 — a −0.995% wobble, well inside the noise. The gate rejected it and reverted the file; the Stockfish tree was left clean. That is the loop being honest: with no real optimization proposed, it declined to claim one. The intelligence that proposes a real change is the agent on the other side of the stdio line; the loop’s job is to measure it fairly and refuse to lie.

Two cleanups

Shipping this surfaced two things worth fixing. The perf backend was removed, as above — Orbit is the profiler this loop is for. And the per-attempt loop log was being committed into the repo: machine- and time-specific run records that go stale and that every run appends to. Those are now generated under a gitignored directory and recreated on demand, the same treatment the capture outputs already had. A run no longer dirties the tree it is trying to optimize.

What is proven

The MCP server answers all seven tools over both framings; the patch sandbox refuses an escape; the mock loop exercises every branch of the gate without touching a target; and on a real, large C++ program — Stockfish — Orbit captured a true profile and the gate made the honest call. What is not here is an agent proposing a winning Stockfish patch: that is the next experiment, and the point of this change is that the machinery to run it safely, and to disbelieve a bad result, now exists.
