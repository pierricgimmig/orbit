Measured 2026-09-02T01:51:33Z on Linux 7.0.0-30-generic, 32 threads.
Commit: 29b0c754d

Write path, taken apart (release build, single thread, release build)
Three runs, medians; from tests/cost.rs.

  owned ring, no clock       6.3 ns    load cursor, store payload, publish
  owned ring + clock        14.1 ns    what an instrumented scope costs
  shared ring, no clock      9.8 ns    the same, with an atomic claim
  shared ring + clock       16.2 ns
  clock read alone           9.3 ns    66% of a real scope
  atomic fetch_add           4.4 ns
  plain increment            0.2 ns
  atomic premium             4.3 ns    what the owned path avoids

  The owned path is the portable one: a thread takes a ring for its lifetime,
  so there is one producer and the cursor needs a load and a store rather than
  a read-modify-write. It saves 3.5 ns of ring cost -- close to the whole
  4.3 ns atomic premium that rseq would have removed, and without a line of
  assembly or a dependency on Linux.

  Growing the record from 32 to 48 bytes to carry inline names cost 2.1 ns in
  isolation and nothing in the real path: the extra stores hide under the
  clock read's latency on an out-of-order core.

  An earlier run reported "98 million events/s, 10.2 ns each" and attributed
  about half of it to the clock. That was wrong: the benchmark pushed a
  pre-built event with a constant timestamp and never read the clock.

  Reproduce:
    cargo test -p orbit-scope-ring --release --test cost -- --nocapture

Layout
  event                    48 bytes (28 fixed + 20 inline name bytes)
  slot                     64 bytes (one cache line: seq + pending_ns + event,
                           exactly, with no padding left)
  ring control block       64 bytes (one cache line, so neighbours never share)
  rings                    one per recording thread, capped at 128;
                           ring 0 is reserved as the shared overflow
  default slots per ring   16384 (1 MiB per ring)

Write path instruction budget, per event, on an owned ring:
  1 x relaxed load         read the cursor (nobody else writes it)
  6 x plain 64-bit store   the payload
  1 x release store        commit the slot
  1 x release store        publish the cursor, after the commit, so a consumer
                           never sees an unfinished slot
  no atomic read-modify-write, no lock, no allocation, no syscall

  On the shared overflow ring, add one relaxed fetch_add to claim the slot and
  one release store to announce the timestamp.

Not measured, and why
  Cross-process throughput. The shared-memory path is exercised by a
  writer and reader in one process; a second process mapping the same
  segment is the next step, together with the C API that fills it.
