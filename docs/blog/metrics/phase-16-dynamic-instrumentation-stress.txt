  Reading: up to 720,000 scopes (1.44 M probe hits) in a second, nothing is
  lost and nothing is at the wrong depth. From 1.44 M scopes/s (2.9 M hits)
  the kernel reports lost records: the per-CPU rings (256 KB each,
  raised to 4 MB on 2026-09-06, see below) overflow before the single
  drain thread (5 ms poll) gets to them, and
  what the kernel drops never reaches the pairing, so the pairing's own
  counts (hundreds) are far below the hole (thousands to a million). The
  same total rate on fewer threads loses more (8 x 20 kHz: 15.9 % against
  16 x 10 kHz: 1.07 %): a thread at 20 kHz pours 360,000 hits/s into one
  CPU's ring, which fills in ~40 ms. The ms-scale maxima in the lossy runs
  are pairing artefacts across a hole, not calls that took that long.

  The healing equation, refined by run 1's sibling 8x5k run (1 dup, 0
  missing): a dropped duplicate costs a scope only when the filter
  misjudged a real call, so missing is bounded by unclosed + orphan below
  and unclosed + orphan + dup above, and with records lost only the floor
  is checked (the 1 % ceiling is what fails).

  The one duplicate in a 360,000-scope run, at 0 missing, is the number
  the filter's future is decided on: it dropped a real re-report once in
  720,000 hits and misjudged nothing.

  Other privileged scenarios through the wrapper, first ever runs:
  instrumentation (63,613 hooked spans, longest 3.39 ms), hook-from-report
  (b3MulW armed, 64 probes), thread-states, self-instrumentation: all pass.

Open: the drain ceiling. Bigger rings and a drain per CPU (or a drain
thread pool) would raise the 1.4 M scopes/s mark; the pairing itself was
not the limit in any run (it never fell behind a ring that had not
overflowed).

Ring size sweep, 2026-09-06, same box, --sudo through tools/sudo. The
per-CPU uprobe ring was 256 KB (UPROBE_RING_KB, uprobes.rs); raised to
4 MB. Under load heavier than the cores the single drain thread is
starved for tens of ms, and a bigger ring tolerates a longer gap. Loss,
256 KB -> 4 MB:

  threads x Hz x calls   scopes/s   256 KB loss    4 MB loss    kernel records lost 256KB -> 4MB
  8  x  5000 x  5000       360k        0.000%         0.000%          0 -> 0
  16 x  5000 x  5000       720k        0.000%         0.000%          0 -> 0
  16 x 10000 x 10000     1.44M         1.04%          0.000%     29,763 -> 0
  8  x 20000 x 20000     1.44M        15.50%          0.000%    445,367 -> 0
  16 x 20000 x 20000     2.88M        45.7%          16.7%      2.58M -> ~0.96M

  The clean ceiling moved from ~720k scopes/s to ~1.44M (2.88 M hits/s);
  the extreme 16 x 20 kHz (5.76 M hits/s) still overflows one drain thread
  but loses a third of what it did. Cost: 4 MB x online CPUs, mapped once
  per instrumented capture (128 MB on 32 CPUs). A drain per CPU or a pool
  is the next lever if the ceiling needs to go higher; the pairing itself
  never fell behind a ring that had not overflowed. The viewer's
  instrumentation status now reads amber when the kernel lost records, so
  a lossy capture is visible.

Drain interval vs ring size, 2026-09-06. Two levers against ring overflow,
measured on the stress test (--sudo). Draining more often is the cheaper
one:

  config                         16x10k    8x20k    ring mem (32 CPUs)
  256 KB ring, 5 ms drain (old)   1.04%    15.50%      8 MB
  4 MB  ring, 5 ms drain (kept)   0.00%     0.00%    128 MB
  256 KB ring, 1 ms drain         0.00%     0.37%      8 MB
  1 MB  ring, 2 ms drain          0.00%     0.00%     32 MB

A 1 MB ring drained every 2 ms holds the realistic loads at zero loss for
a quarter of the 4 MB ring's memory. The drain interval is not simply
minimised because the same loop paces the live WebSocket batches (2 ms is
2.5x the traffic of 5 ms, 1 ms is 5x). Left at the roomy 4 MB / 5 ms
default; both are now env-configurable for tuning without a rebuild:
ORBIT_UPROBE_RING_KB (power of two KB, >= 4) and ORBIT_DRAIN_MS (1..=100).
Under the tools/sudo wrapper they must be in its sudoers env_keep.
