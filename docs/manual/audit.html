Shortcomings · leftovers · tests · footguns

Audit

This is a reading of the tree, not a load test. Items below are things the code actually does (or does not do). Severity is about user impact on a current Linux box, not about elegance.

What this review could not do

  • No OrbitQt build — Qt5 packages were not present.
  • No LinuxTracing build — gRPC/protobuf/LLVM/Conan graph not installed; py-spy FFI needs Cargo.
  • No perf_event_open of an uprobe — no PMU, no uprobe_events.
  • No integration tests, no ORBIT_UPROBE_BENCH=1. No milliseconds claimed.
  • PR #10 inspected via git log / git diff --stat against main, not merged.

High-impact shortcomings

1. Uprobe stop scales with cores × functions

Current OpenUprobes + sequential close is the product’s most expensive teardown. User-space instrumentation is the default partly because of this (the UI literally says uprobes are “slower”). On a 16–32 CPU machine with dozens of hooks, stop can dominate the session. The fix direction is already designed on cursor/fast-uprobe-stop-a3cf. Leaving it unmerged is a product bug, not a research gap.

2. Tracepoint IDs are debugfs-only

GetTracepointId will not see a modern-only tracefs mount. Scheduling, thread names, GPU, and custom tracepoints then fail together. Easy to fix; unfixed for years.

3. uprobe_type() / max_stack() can throw

Static initialization via ReadFileToString().value() + std::stoul is not an ErrorMessageOr. A container kernel without the PMU can abort the tracer thread instead of emitting the existing protobuf error event.

4. CI does not run the tests that need a real kernel

.github/workflows/build-and-test.yml Ubuntu step:

ARGS="-E IntegrationTest" ... cmake --build . --target test

So LinuxTracingIntegrationTests and OrbitServiceIntegrationTests never run on GitHub Actions. GPU tests also require CheckIsStadiaInstance() (kernel release contains -ggp-). Unit tests cannot replace “did perf_event_open actually fire?”. A regression in OpenUprobes can merge green.

Ubuntu CI also configures CMake without Conan (system packages). The README’s happy path is Conan 2. Windows CI still pins Conan 1.58.0. Three build stories, one repo. Actions still use checkout@v3 / cache@v3 / upload-artifact@v3.

Poor implementation / footguns

  • Partial uprobe success. OpenUserSpaceProbes continues after a failed function, sets a boolean, and still enables the fds that worked. The UI gets a generic “uprobes” failure string, not per-function errors (those exist only for the “not in a file mapping” warning).
  • ioctl / close errors ignored. perf_event_enable/disable/redirect log and proceed. close return value is discarded. Teardown can look clean while probes remain.
  • TracingHandler one-shot. After Stop, late FunctionEntry events are dropped. A second Start on the same object is forbidden by comment, not by API.
  • 333 ms reorder delay. Always. Short captures and “stop and see the last slice” pay it. Not configurable.
  • Python auto-on. Any exe whose basename contains python gets a py-spy attach (ptrace). That can fail noisily or surprise a user who did not ask. Detection misses embedded interpreters.
  • py-spy FFI build. LinuxTracing unconditionally PRIVATE pyspy_ffi. If Cargo is missing, CMake warns and return()s from the FFI file — the imported target may not exist and the LinuxTracing configure/link becomes environment-dependent. No test binary covers PythonProfiler.
  • Insecure gRPC on localhost is fine behind SSH; it is not fine if someone rebinds the flag. There is no peer auth on the Unix producer socket either (filesystem permissions only, /tmp/...).
  • Memory watchdog = 50% of physical RAM. In a small cgroup this is either never hit or hit immediately. It reads host sysconf(_SC_PHYS_PAGES), not cgroup memory.max.
  • cgroup v1 only for cpuset and for memory tracks that still talk about ggp run --enforce-production-ram (CGroupAndProcessMemoryTrack.cpp).
  • Round-robin batch of 5 treats a stack sample like a sched_switch. The TODO in Run admits this. Under load, sampling buffers (16 MiB) and uprobe buffers (8 MiB) can still LOST.
  • Wine / PE anonymous maps — uprobes silently do not fire; the warning exists but only if maps were readable at start.
  • ARM64 docs vs code. building_arm64.md says dynamic instrumentation is “uprobes-based” and unsupported. Code: trampolines unsupported, uprobe PMU wired.

Stadia / GGP / cloudcast leftovers

These still compile and still run on the hot path:

  • PrintInstanceVersions — four cloudcast reads + gpuinfo on every service start.
  • Minidump directory /usr/local/cloudcast/core for capture-finished process state.
  • src/OrbitClientGgp, OrbitCaptureGgpClient, OrbitCaptureGgpService, services_ggp.proto, port 44767.
  • GGP_SDK_PATH symbol provider; ggpvlk.so load priority; FakeClient instruments ggpvlk QueuePresentKHR.
  • CheckIsStadiaInstance — GPU integration tests are dead on any non--ggp- kernel.
  • Comments referring to CloudCollectorStartStopCaptureRequestWaiter (type not in tree).
  • copybara:insert blocks in UserSpaceInstrumentation and OrbitBase tests.
  • Toolchain file third_party/toolchains/toolchain-linux-ggp-release.cmake.

None of this is “wrong” if Stadia support is still a goal. If it is not, it is noise that hides real errors (every laptop start logs four ORBIT_ERRORs from missing VERSION files).

Windows vs Linux completeness

README is accurate. Windows has ETW sampling, module/thread snapshots, optional API-in-tracee. It does not have dynamic hooks, sched tracepoints, uprobes, user-space trampolines, or the Linux memory watchdog. Shipping a Windows UI that talks to Linux OrbitService is the supported remote story. Local Windows profiling is a remnant.

GPU path assumptions

Driver timeline is AMD-only. Vulkan debug markers need src/OrbitVulkanLayer loaded in the target and the producer socket. Tests for GPU jobs are Stadia-gated. Raspberry Pi and Intel/NVIDIA users get a checkbox that fails open.

Error handling quality (honest summary)

The codebase is not sloppy about logging. Almost every perf_event_open failure is ORBIT_ERROR’d. The gap is recovery and specificity: one boolean for “some uprobes failed”, exceptions on missing sysfs, no retry, no capability probe at service start, no structured “this kernel cannot do X” before the user hooks 80 functions.

Thread safety in the tracer is mostly “one run thread + one deferred thread + mutex on the staging vector.” Visitors are not concurrent. UI OrbitApp hops to the main executor for almost every event — correct, and a bottleneck under huge captures (not measured here).

Dead or disabled tests elsewhere

Several tests are compiled but disabled with Google Orbit issue links: OrbitBase/ThreadPoolTest.cpp (#4503), ObjectUtils/ElfFileTest.cpp (#4502), WindowsUtils/ProcessLauncherTest.cpp. Those are inherited, not introduced here.

What is actually in good shape

Credit where the tree deserves it:

  • Visitor split and 333 ms reorder are a clear, documented design — not an accident.
  • User-space and kernel paths sharing UprobesFunctionCallManager is the right abstraction.
  • Wine stack-switch handling is specific and commented.
  • Capture file format is versioned and documented (FORMAT.md).
  • Unit tests around unwind + mmap updates are thorough as fixtures.
  • This fork’s ARM64 register work and py-spy integration are real features, even if the latter is still young.
