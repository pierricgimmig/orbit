Architecture

Orbit is a two-process product plus the target. The UI never opens perf_event_open. The service never draws a track. A third channel exists for in-process producers that cannot go through the UI.

The three processes

Orbit (UI)

Entry is src/Orbit/main.cpp. Qt chrome lives in src/OrbitQt (orbitmainwindow.cpp, capture options, connection dialogs). The capture canvas, tracks, and session state live in src/OrbitGl: OrbitApp, TimeGraph, TrackManager, SymbolLoader. OrbitApp is the god object; comments in OrbitApp.h already ask to peel controllers off it.

The UI talks to the service through generated gRPC stubs in src/GrpcProtos. Default port is 44765 (FLAGS_grpc_port in src/ClientFlags/ClientFlags.cpp and src/Service/main.cpp). The server binds 127.0.0.1 with InsecureServerCredentials (OrbitGrpcServerImpl::Init). Remote use is an SSH tunnel, not TLS.

OrbitService

src/Service/OrbitService.cpp starts the gRPC server and, unless --producer_side_server=false, a second server on the producer-side Unix socket. On Linux, OrbitGrpcServer.cpp registers:

  • LinuxCaptureService — bidirectional Capture stream
  • ProcessServiceImpl — process list, modules, debug-info path, process memory
  • TracepointServiceImpl — enumerate kernel tracepoints
  • CrashServiceImpl — only if dev_mode

On Windows the same process registers WindowsCaptureService and WindowsProcessService. There is no Windows tracepoint or crash service in that file.

At startup on Linux, PrintInstanceVersions runs uname -a and then tries four Stadia/cloudcast paths (/usr/local/cloudcast/VERSION, BASE_VERSION, INSTANCE_VERSION, and /usr/local/cloudcast/bin/gpuinfo). Failures are logged as errors on every ordinary Linux box. See the audit.

Target + optional in-process producers

The target is identified by pid in CaptureOptions. User-space instrumentation injects liborbituserspaceinstrumentation.so and overwrites prologues. The Orbit API (src/Api, enabled via ApiLoader/EnableInTracee.h) and the Vulkan layer (src/OrbitVulkanLayer) connect as producers to unix:/tmp/orbit-producer-side-socket (src/ProducerSideChannel/include/ProducerSideChannel/ProducerSideChannel.h).

Capture start / stop

The Capture RPC itself is thin: LinuxCaptureService::Capture builds a GrpcClientCaptureEventCollector over the ServerReaderWriter, waits for the first CaptureRequest (the options), then calls DoCapture. A second capture while one is live returns ALREADY_EXISTS.

Why stop is parallel at the service layer but serial in the tracer. Comments in LinuxCaptureServiceBase.cpp say TracingHandler::Stop and producer OnCaptureStopRequested both block, so they are joined on separate threads. Inside the tracer, Shutdown still close()s fds one by one. Parallelizing those closes does not help on current kernels — see kernel assumptions.

Event path: kernel → UI

User-space instrumentation does not emit timers on its own path into the UI. ProducerEventProcessorHijackingFunctionEntryExitForLinuxTracing intercepts FunctionEntry / FunctionExit and calls TracingHandler::ProcessFunctionEntry/Exit, which forwards into TracerImpl. UprobesFunctionCallManager then builds the same FunctionCall objects it would for uretprobes. That is why trampolines and uprobes can share the unwinder and the call-stack patching logic.

gRPC surface

Protos live under src/GrpcProtos/. The capture contract is capture.proto. CaptureOptions (next id 23 in the comment, with later Python fields at 24+) is the one large message: pid, sample rate, stack dump size, unwinding method, dynamic-instrumentation method, instrumented functions, Wine helpers, GPU flag, memory sampling, API functions, thread-state callstack policy, Python flags.

The receive size on the server is INT32_MAX so an unbounded options message can arrive. There is no authn/authz on the channel.

Producer-side channel

ProducerSideServer implements CaptureStartStopListener. On capture start it is given the hijacking processor so API scopes from the injected library and Vulkan debug markers join the same stream. Socket path: /tmp/orbit-producer-side-socket. Windows uses localhost:1789 instead. The injected user-space library calls CreateProducerSideChannel() from OrbitUserSpaceInstrumentation.cpp.

Memory watchdog

WaitForStopCaptureRequestOrMemoryThresholdExceeded polls OrbitService RSS every second via /proc/self/stat field 24 (MemoryWatchdog.cpp). Threshold is half of physical RAM (kMemTotalBytes / 2). Crossing it stops the capture with StopCaptureReason::kMemoryWatchdog. This is a service-side safety net, not a UI setting (the UI has a separate, flag-gated warning-threshold checkbox).

Windows path (what exists)

WindowsCaptureService::Capture enables the API in the tracee, starts WindowsTracing::TracerImpl (krabsetw ETW: sampling + modules + thread names), notifies producers, waits for stop, disables the API, stops the tracer. There is no InstrumentationManager, no uprobes, no sched tracepoints, no memory watchdog loop like Linux. WindowsTracing/TracerImpl.cpp is short: snapshot modules (Toolhelp, fallback ETW), snapshot thread names, run KrabsTracer.

Capture file

On-disk format is documented in src/CaptureFile/FORMAT.md: 4-byte signature ORBT, version, capture-section offset, optional extra sections, optional user-data section. The capture section is a sequence of ClientCaptureEvent messages starting with CaptureStarted and ending with CaptureFinished. The UI can reload a file without a service.

Stadia-shaped stop. After stop, GetTargetProcessStateAfterCapture looks for minidumps matching .*<pid>.<epoch>.core.dmp under /usr/local/cloudcast/core. On a machine without that directory the function either reports “still running”, “ended”, or an internal error — never a Stadia crash. Comments still mention CloudCollectorStartStopCaptureRequestWaiter, which is not a type in this tree.
