Orbit's Linux build now runs on Bazel. git clone, git submodule update --init third_party/py-spy, bazel build //... — that is the whole setup. No Conan, no CMake, no apt install, no Rust toolchain. This is the reasoning behind each decision, including the two that were wrong the first time.

What was there before

81 module directories under src/, about 1,220 C++ source and header files, one Rust crate, and a Qt 5 desktop UI. CMake drove the build; Conan supplied Abseil, protobuf, gRPC, GoogleTest, LLVM, capstone, OpenSSL, libssh2 and Outcome; Qt came from the system via apt install qtbase5-dev; and eleven more libraries were vendored directly into third_party/, each of which now has its own BUILD file.

The cmake/Find*.cmake directory is the interesting part of the old setup — twenty-four hand-written find modules, several with fallback chains (try the Conan package, then pkg-config, then build it from third_party/). That is the machinery the port had to replace, and it is also a good map of where the sharp edges were.

The one principle

You asked for Bazel modules instead of Conan, and for the first build to be fast. Those two pull in opposite directions: a Bazel module means source, and source means compiling. So the rule for every dependency was:

Rule
Use a Bazel module when one exists and the compile is affordable. Where it isn't affordable, fetch a prebuilt artifact pinned by URL and SHA-256 — never reach for something already installed on the machine.

That last clause is what keeps the build honest. "Prebuilt" here does not mean "whatever apt put in /usr"; it means a specific file, at a specific URL, with a specific hash, recorded in the repository. A different machine gets the same bytes.

Where each dependency comes from

Four paths, in descending order of preference.

The one thing the host still provides is the low-level shared libraries Qt itself loads — ICU, glib, fontconfig, X11. Those are present on any desktop install and are the same libraries the CMake build linked against.

Qt: prebuilt, from pinned .debs

Qt is where the "affordable compile" test fails hardest. Building Qt 5 from source would have dwarfed everything else in a first build, and there is no Qt 5 Bazel module — rules_qt in the registry is Qt 6 only. The old build sidestepped this by requiring apt install qtbase5-dev, which means the build depends on machine state and on having root.

Bazel can extract the outer ar container of a .deb natively. That turns out to be the whole trick: a repository rule downloads the package, lets Bazel unpack the container, picks data.tar.zst back out, and unpacks that over a shared tree. No host tools, no dpkg, no root.

Three small libraries had to be added to that set — libdouble-conversion3, libpcre2-16-0, libmd4c0 — because libQt5Core and libQt5Gui need them and Ubuntu 26.04 does not ship them in a default install. To bump Qt, edit the package list in bazel/deps/resolve_debs.py and re-run it; it rewrites debs.bzl from apt metadata.

The plugin problem

libQt5Core has the Ubuntu package's install prefix compiled into it and looks for platform plugins underneath it. Since Qt was never installed, that path does not exist and QApplication refuses to start. Qt reads a qt.conf next to the executable before falling back to the built-in prefix, so qt_application() writes one and mirrors the plugin tree into the same output directory. bazel-bin/src/Orbit/Orbit now starts standalone.

LLVM: built, and patched twice

LLVM was the decision most likely to blow the build-time budget, so it got measured first. Orbit links six libraries — Object, Symbolize, DebugInfoDWARF, DebugInfoPDB, DebugInfoCodeView, Demangle — and Bazel builds only what is reachable. That subset compiles in about 40 seconds, not the hours a full LLVM build takes, so the registry module won and no prebuilt tarball was needed.

It needed two patches, both in bazel/patches/.

1 · The missing include

SmallVector.h names uint64_t without including <cstdint>. Older libstdc++ headers dragged the declaration in transitively; GCC 15's do not, so every translation unit that reaches SmallVector.h — LLVM's own and Orbit's alike — failed to compile. Upstream fixed this after 17.0.4; the patch backports the one-line include.

2 · The missing zlib

LLVM's Bazel overlay has the zlib dependency commented out, which makes every attempt to read a SHF_COMPRESSED debug section fail with "LLVM was not built with LLVM_ENABLE_ZLIB". Orbit reads compressed debug info from real binaries, and ObjectUtilsTests caught it immediately. Restoring it means adding LLVM_ENABLE_ZLIB=1 and a dependency edge — but the edge needs zlib to be visible inside llvm-project, which means adding a bazel_dep to its MODULE.bazel.

Why archive_override, not single_version_override

Module resolution reads the MODULE.bazel the registry serves, not the one in the archive, so a patch to it under single_version_override is simply ignored. archive_override reads the module file from the archive, which makes the patched bazel_dep take effect. The archive URL and integrity are copied verbatim from the registry's own source.json, so the same bytes are fetched either way.

The SSL problem

This one took three attempts and is the most interesting thing in the port.

gRPC links BoringSSL by default. libssh2 links OpenSSL. Both export the OpenSSL C API, and the Orbit UI needs SSH and gRPC — so it failed to link with hundreds of duplicate definitions: CONF_modules_load_file, X509V3_EXT_nconf, i2v_GENERAL_NAMES, on and on.

The obvious fix is to make gRPC use OpenSSL too; it has a flag for exactly that. The UI then linked. But UserSpaceInstrumentationTests started failing in a way that took a while to pin down: the library Orbit injects into a target process would load, initialise, and produce no threads at all. Reproduced outside Bazel with a twelve-line dlmopen harness, it was blunter than that — corrupted double-linked list, then SIGABRT. OpenSSL's initialisation does not survive being loaded into the fresh linker namespace dlmopen(LM_ID_NEWLM) creates. The same harness against a BoringSSL build printed init returned and 21 threads.

So: BoringSSL breaks the UI, OpenSSL breaks injection. The third option is to notice that Orbit never uses TLS at all. Every channel and every server in the tree is built with InsecureChannelCredentials or InsecureServerCredentials — ten call sites, no exceptions — because the transport is either a Unix socket or a tunnel SSH has already secured. That is also what the pkg-config fallback in cmake/FindgRPC.cmake selected: grpc++_unsecure.

gRPC builds grpc++_unsecure but keeps it behind an empty package group, so the module carries a one-line patch changing that target's visibility to public. That is the third patch in bazel/patches/.

To be explicit: this drops no security

The target's name invites the opposite reading, so it is worth stating plainly. Orbit has never used gRPC's TLS. All ten channel and server call sites use InsecureChannelCredentials or InsecureServerCredentials; grpc::SslCredentials has never appeared anywhere in this repository's history; there is no certificate, key or PEM handling in the tree. Linking grpc++ compiled a TLS stack that no code path could reach, and removing it changes no runtime behaviour.

What protects each link, and always did:

LinkWhat protects it
Client → OrbitServiceThe server binds 127.0.0.1 only, so it is not reachable from the network. Remote profiling reaches it through an SSH tunnel, which is what authenticates and encrypts the link.
Producer → OrbitServiceA Unix domain socket, governed by filesystem permissions.
Symbol downloadsReal HTTPS — but through Qt, not gRPC. Untouched by this change.

TLS on a loopback socket would add nothing to the first row: anything that can open that port can also complete a handshake with it.

The one place TLS is real

Debug symbols are fetched over HTTPS from the Microsoft symbol server, through QNetworkAccessManager. Qt resolves its TLS backend by dlopening libssl at runtime, which means a Qt without a usable one fails every https:// request at runtime and nowhere else — no link error, no warning. Since this build supplies Qt from pinned packages rather than from the machine, that property is now asserted rather than assumed:

[ RUN      ] Tls.QtCanDoHttps
[       OK ] Tls.QtCanDoHttps

The Qt shipped here is built against OpenSSL 3.5.3 and resolves 3.5.5 at runtime.

Exposure that does exist, and predates this port

OrbitService's gRPC endpoint has no authentication at all, and the service is normally run as root so that it can ptrace, read /proc/*/mem and inject libraries into arbitrary processes. Loopback keeps it off the network, but any local process can still connect and ask for those operations.

Adding TLS would not close that. Authenticating the peer would: a Unix domain socket with restrictive permissions — the pattern the producer side already uses — or an SO_PEERCRED check on the connection. That is a change to the service rather than to the build, so it is not part of this port.

Every version that moved

Most of these jumps were not chosen so much as forced. Bazel 9 removed the native cc_library from BUILD files, and older registry modules — and the rule sets they pull in transitively — have not caught up. Pinning gRPC near its old 1.67 was tried and abandoned: 1.72 loads, but its BUILD files want @protobuf//bazel:upb_proto_library.bzl, which protobuf 30 deleted, and minimal version selection pushes protobuf to 35 regardless because envoy_api and rules_go ask for it.

Removed along the way

An explicit rules_foreign_cc dependency was needed briefly, to force a Bazel-9-compatible version over the one gRPC's telemetry libraries pulled in. Once gRPC moved to 1.83 it became unnecessary and was taken back out.

Writing 72 BUILD files

The CMakeLists.txt files are strikingly regular — a library, its sources, its dependencies, a test binary, register_test — so they were translated mechanically rather than by hand. bazel/tools/cmake2bazel.py parses the CMake command stream, evaluates the conditionals for a Linux build with the GUI on, and emits BUILD.bazel. It is checked in so the port can be re-derived and diffed against CMake, not because the build needs it.

It handles a few things that are easy to get wrong by hand:

  • Headers CMake never had to list. CMake compiles fine without naming private headers; Bazel needs every included header declared. The translator adds any header in the module that the CMakeLists did not mention.
  • if(WIN32) branches. Sources inside them are still collected, purely so their headers can be kept out of the Linux target rather than swept up by the rule above.
  • PUBLIC vs PRIVATE include directories. Public ones become includes and propagate; private ones become -I flags in copts and do not.
  • Qt macros. Headers are scanned for Q_OBJECT, Q_GADGET and Q_NAMESPACE to decide what moc has to run on, and .ui files are globbed the way AUTOUIC finds them.

Everything it could not model is either hand-written (the two proto packages, the version file, the gtest entry points, the API header's C compile test) or listed in small tables at the top of the script — extra runtime data, the tests that need a binary copied next to them, the one test marked flaky.

Qt code generation

CMake's AUTOMOC and AUTOUIC scan sources at build time and generate whatever they find. Bazel needs the generated files named before the build starts, so qt_cc_library takes them as attributes.

One detail worth recording, because it is invisible until it breaks: moc writes an #include of the header it processed into the generated file, and the path it writes has to resolve from the generated file's own directory. The rule passes -f with the header's path relative to whichever include directory exposes it — falling back to the workspace-relative path for private headers, which resolves through the -iquote entry Bazel adds anyway.

Protos

Orbit's .proto files import each other by bare filename (import "capture.proto";) while the generated C++ is included with a module prefix ("GrpcProtos/capture.pb.h"). proto_library cannot express both — strip_import_prefix satisfies one or the other. Rather than rewrite thirteen proto files, bazel/proto/rules.bzl drives protoc directly, the same way cmake/grpc_helper.cmake did. Both proto packages are self-contained, so one generation step per package is exactly the right granularity.

Two include-path quirks

Both come from the same place: Conan exposed every package's headers through one include directory, so Orbit spells third-party includes with angle brackets — #include <absl/strings/str_cat.h>. Bazel publishes a module's headers through -iquote, which only satisfies quoted includes. Rewriting 1,159 absl includes across the tree was one option; the other was to add the repository root as a system include directory. Label(…).workspace_root resolves to the canonical repository path at load time, so bazel/copts.bzl computes the flag rather than hard-coding external/abseil-cpp+.

The second quirk is warnings. Orbit compiles with -Werror=old-style-cast, among others, and third-party headers do not survive that. Bazel's external_include_paths feature switches external repositories to -isystem, which handles the registry modules — but not the code vendored inside this repository, which is not "external" as far as Bazel is concerned. The directories cmake/Find*.cmake marked SYSTEM are therefore listed explicitly in copts.bzl; without it, gte's headers alone produce about 4,000 errors.

Source changes, and why

Fourteen files, +132/−62, each change in its own commit. None of it is Bazel-specific — it is what the newer dependency versions require, plus two genuine bugs that the newer versions exposed.

Forced by protobuf 36

Arena::CreateMessage was removed in protobuf 31. Arena::Create has been the spelling for messages far longer and works with both, so the change is backwards-compatible with the Conan build.

Forced by LLVM 17

Elf_Note_Impl::getDesc gained a required alignment argument, which the section header carries. This is the one change that is not backwards-compatible: LLVM 13, which Conan pins, has the no-argument form.

Forced by GCC 15

Vendored procinfo/process.h names uint64_t without including anything that declares it.

A real hash bug

Abseil's newer hardened builds assert that eq(a, b) implies hash(a) == hash(b), and ClientModelTests aborted on it. The transparent hash functor in SamplingDataPostProcessor hashed a CallstackInfo through its AbslHashValue, which combines (type, frames) — but hashed the heterogeneous lookup key as a std::pair, which combines (frames, type). Keys that compare equal hashed differently, so the heterogeneous lookup the functor exists for could never find anything, and every callstack was inserted afresh. Both overloads now go through one expression.

Thread exclusion that outlived its assumptions

When Orbit injects liborbituserspaceinstrumentation.so into a target, that library starts threads of its own. The instrumentation payload must skip them, or it recurses into the code reporting the events — so OrbitService finds them after injecting and hands their ids back.

It did that by waiting for exactly five threads with hard-coded names, two of which came from gRPC's internal executor. gRPC deleted the executor in 1.73 in favour of an event engine whose pool is sized by core count. The set never matched again, so instrumentation failed outright — and the count is no longer fixed, which the six-argument SetOrbitThreads could not express.

Two tests that asserted CMake's output layout

ExecutablePathTest asserted the test binary sits in a directory named bin — which says nothing about GetExecutablePath and everything about where CMake puts binaries. The copybara note directly above it says as much: Google's internal build skips the test because its directory is named differently. GetTestLibLibraryPath looked for its library only in ../lib for the same reason, and now checks next to the executable first, which is where every other library lookup in the tree starts.

Behaviour change worth knowing about

//src/OrbitVersion is generated from --workspace_status_command. Everything it reports is derived from the commit rather than from wall-clock time, so an unchanged checkout produces an unchanged binary and no needless relinking. The build timestamp is now the commit's date, not the moment you ran the build.

Where the 6m35s goes

Measured on this machine — 32 cores, empty output base, empty disk cache, nothing downloaded:

$ bazel build //...
INFO: Elapsed time: 394.796s, Critical Path: 101.22s
INFO: Build completed successfully, 9520 total actions

Three things keep that number where it is.

Qt is not compiled. It is unpacked. That alone is the difference between six minutes and something closer to an hour.

The TLS stack is not built. Choosing grpc++_unsecure removed roughly 2,500 targets — BoringSSL, and everything in gRPC that only exists to feed it.

A shared disk cache. .bazelrc points --disk_cache at ~/.cache/bazel/orbit, which is keyed by action rather than by output base. Deleting bazel-out, switching branches, or making a second clone re-uses it, so the expensive dependency compile happens once per machine rather than once per checkout. The 6m35s above is the pessimistic case where even that is empty.

Two figures for scale: LLVM's six libraries take about 40 seconds, and py-spy with the 213 crates in its lockfile takes 43. A no-op rebuild is under a second. Put machine-specific settings — --jobs, a remote cache, a different cache location — in .bazelrc.user, which is git-ignored and imported automatically.

Test results

bazel test //... runs 49 targets; 48 pass. Getting there needed the tracing surface switched on, which is what turned two of the defects in this port up:

$ sudo sysctl -w kernel.perf_event_paranoid=-1 kernel.yama.ptrace_scope=0

Before that, LinuxTracingIntegrationTests reported success while skipping its own body — it gates on IsRunningAsRoot() || perf_event_paranoid <= N. Once it actually ran, it found that cc_test links dynamically where cc_binary does not, so the test binary was split across a shared object per module and a test that reads its own symbol table found nothing there.

The one failure

InstrumentProcessTest.Instrument fails on about four runs in five when run on its own, and two full-suite runs in three; one full bazel test //... has come back 49 of 49. It is a defect in the injection, not in the build — and it is a race, with the timing as the evidence.

Adding two ORBIT_LOG calls around the body of InitializeInstrumentation — nothing else — makes the test pass consistently. The failure rate inverts with machine load. Waiting five times longer on the OrbitService side does not help, because the producer's threads are never created at all rather than created late.

ConditionResult
Run on its own, unmodifiedfails 4 runs in 5
Two log lines added around the initialisationpasses
Under full-suite loadfails 2 runs in 3
OrbitService waits 5× longer for the threadsstill fails

The shape of it: OrbitService clones a thread into the target with CLONE_VM | CLONE_THREAD and, deliberately, no thread-local storage of its own. MachineCodeForCloneCall says as much: "we do not create a new data structure for thread local storage but use the one of the thread we halted." That thread calls InitializeInstrumentation, which starts the producer's connect thread through std::thread, then exits immediately through a raw SYS_exit. Anything that delays that exit makes the problem disappear.

A standalone harness reproducing the borrowed-TLS thread model segfaults every time, which shows the model is fragile. It is not proof of the cause here, though: that harness leaves the TLS owner running concurrently, where ptrace has it halted, so it is harsher than the real path.

Fixing it means making the injected thread wait until the producer's threads exist rather than relying on timing — inside ptrace-injected machine code, and a change to the product rather than to the build. It is the same area the upstream GTEST_SKIP in that test cites (b/237251106).

What still needs actual root

Seven integration tests call geteuid() == 0 directly and skip otherwise — SchedulingSlices, FunctionCalls, two callstack-with-uprobes tests, ThreadStateSlices, ThreadNames, and GpuJobs (which also wants Stadia hardware). No sysctl or permission change unskips them: they read kernel tracepoints under /sys/kernel/debug/tracing, which is 0700 root. Running the test binary under sudo is the only way.

Timing, not correctness

Three tests carry Bazel tags instead of changed assertions. The integration tests are exclusive: they assert that no perf records were lost and no events were discarded as out of order, which is only true on a machine that is not saturated — run alongside 48 other tests, the ring buffer legitimately overflows and the tracer correctly reports it. SessionSetupTests and CaptureEventProducerTests are flaky: one waits 500 ms for a 250 ms timer, the other sleeps 25 ms and expects a gRPC round trip inside it.

What is not ported

The Bazel build covers exactly what the top-level CMakeLists.txt builds on Linux. Three groups sit outside it, matching what CMake leaves out there too: the src/Windows* modules behind if(WIN32); the three Vulkan modules behind WITH_VULKAN, an option the root CMakeLists.txt leaves commented out so neither build system produces them; and FuzzingUtils, whose add_subdirectory is commented out.

Every CMakeLists.txt is still in place. Windows and the ARM cross-build still use them, and the README now says so.

CI will fail on this branch

build-and-test.yml runs the CMake + Conan build on pull requests touching src/**, and conanfile.py pins llvm-core/13.0.0 — which predates the getDesc signature above. That single line is the only thing that breaks it.

Two ways out: move the Conan pin to LLVM 17 or newer, or point CI at Bazel. The second is a smaller workflow file than the first is a dependency bump.
