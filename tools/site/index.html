Then time the hot functions

Auto-profiling hooks the functions the samples point at and drops whatever costs too much, inside a budget you set. No rebuild and no source edits. On Linux it needs root or CAP_SYS_ADMIN. It is not available on macOS or Windows. You can also hook one function yourself.

How it works

The capture agent runs on the machine you profile. The viewer is a web page, so you can open it on another device.

In the manual

  1. Target process

    Already running

    A native binary. perfr does not rebuild it and does not relaunch it.

  2. perfr

    What this machine records

    On Linux: call stacks at 1 kHz, the scheduler, and dynamic instrumentation with no code change. Auto-profiling picks what to hook and keeps the cost under a budget. It needs root or CAP_SYS_ADMIN. On Windows: the same call stacks, scheduler and thread states from the kernel logger, which needs an elevated prompt; Frida hooks and manual scopes without one. On macOS: manual scopes and Frida function hooks. Sampling, the scheduler, and auto-profiling are not in that build.

  3. Web viewer

    Live, in the browser

    Timeline, flame graph, call trees, live table, selection reports, and, on Linux and Windows, disassembly (next to source on Linux).

  • Linux is the x86-64 service. Sampling is fixed at 1 kHz and unwound with DWARF. Arm64 has the register and unwind paths and is not run in CI; the static binary is x86-64.
  • macOS function hooks are tested on Apple Silicon and Intel. Attaching needs a task port. Code signing, the hardened runtime, and SIP can refuse it; these builds do not bypass that. Shared-cache images whose symbols Frida cannot read may be missing from the function list. Hook-safety analysis is the Linux path. The release binary is universal and ad-hoc signed, not notarized.
  • Dynamic instrumentation needs no code change. Frida is the default. On Linux, auto-profiling uses a kernel engine and needs root or CAP_SYS_ADMIN.
  • Auto-profiling is supported on Linux and needs root or CAP_SYS_ADMIN. It is not available on macOS or Windows.
  • Windows is the x86-64 service. Sampling (1 kHz, the kernel walks the stacks), the scheduler and thread states come from the NT Kernel Logger (ETW), which needs a prompt opened with Run as administrator; manual scopes and Frida hooks need no privilege. Symbols come from PDBs and export tables. Disassembly is partial: there is no source interleave, since the line table lives in the PDB. No GPU lanes. The binaries link the C runtime statically and are not code-signed.

Get started

The script installs the build for this machine, including the Frida files function hooks need.

Run it

# install (Linux x86-64 or macOS)
curl -fsSL https://raw.githubusercontent.com/perfr/perfr/main/tools/install/install.sh | sh

# install (Windows x64, PowerShell)
irm https://raw.githubusercontent.com/perfr/perfr/main/tools/install/install.ps1 | iex

perfr
# http://127.0.0.1:44766/

The scripts download a GitHub Release tagged perfr-v*. Linux x86-64, macOS (one universal binary, Intel and Apple silicon) and Windows x86-64 are all in that release. Until a stable release exists the script stops and says so. Function hooks ship beside the binary and do not need root. On macOS, attaching needs a task port.

On Linux, sampling works at perf_event_paranoid 2 or below, and the scheduler needs 0 or below. Root, CAP_PERFMON or CAP_SYS_ADMIN bypass the sysctl. Auto-profiling needs root or CAP_SYS_ADMIN. On Windows, sampling, the scheduler and thread states need a prompt opened with Run as administrator. Those are not in the macOS build.

Where it runs

The service runs on the machine you profile. The viewer runs in any browser, on any device, including a phone.

Several machines go on one timeline: start the service on each with --join <hub>:44766 and the hub's viewer shows them all, clocks aligned over the link, one Record for every machine. Several machines in the manual.
