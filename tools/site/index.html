Orbit is a profiler for native applications. Hook the functions you care about on a running process, without recompiling, and see every call as a scope on a timeline that draws a million of them at the screen's refresh rate, with a sampling profile underneath that says where the rest of the time went.

Python on one side, native + CUDA on the other — one timeline

The one thing no other profiler does: dynamic instrumentation on both sides of the Python boundary, in a single capture. Your Python functions, the C extension they call into, and the GPU kernel it launches — aligned on one timeline.

Zero code

Attach and see it

CPython built --with-dtrace carries USDT probes Orbit reads from outside the process — your Python functions become scopes with no imports, no decorators, no restart. Where a build omits the per-function probes, Orbit says so and falls back to sampling.

The half everyone misses

Into the C extension

The Python probes stop at the C boundary — and in AI workloads that is where the time goes. Orbit's native instrumentation catches NumPy, PyTorch and the CUDA kernels they launch, so one capture shows the whole stack: Python wrapper → C extension → GPU.

For AI work

One machine or a cluster

Profile a training loop end to end — framework overhead, the native kernels, and the GPU — on a single box or across a cluster on one timeline. The differentiator for ML performance work.

What it does

One timeline, three sources of truth about where the time goes.

The mode

Dynamic instrumentation

Pick a function in the sampling report, or search for it, and hook it: entry and exit become a scope on the thread that called it, with its duration, count and distribution in the Live tab. Kernel uprobes, no rebuild of the target.

Underneath it

Sampling

Callstacks at a fixed rate on every thread, DWARF or frame-pointer unwound, symbolized from the binaries and their debug files. Flat report, top-down and bottom-up trees, a flame graph, and reports scoped to a selection, a thread, or every instance of one scope.

When you know the name

Manual instrumentation

One header, one static library: orbit_start / orbit_stop, async spans, links, values. Rust, C, C++ and Python. Anything that can run a command uses orbit-scope.

The API →

Processes, machines, platforms

Every process the service sees, on one timeline with the scheduler under them. A machine row per service, from any host on the network. The service is one static binary; the viewer is a web page.

Run it

# install (Linux / macOS, no package manager)
curl -fsSL https://orbitprofiler.dev/install.sh | sh

orbit-service --serve 44766
# Orbit live viewer: http://127.0.0.1:44766/
#                    http://192.168.1.10:44766/

The banner prints the LAN address; open it from any machine. Sampling needs perf_event_paranoid at -1 or CAP_PERFMON; dynamic instrumentation needs CAP_PERFMON.

Where it runs

Linux on x86-64 and arm64 today, as one static binary. Windows and macOS capture are in progress. The viewer runs wherever there is a browser, and a saved capture opens as a file, like the one above.

Captures are Parquet in a zip; a slice of one is cut on disk without reading the rest, and pandas opens them with nothing to install.
